## 1. Purpose

P1 gave the platform one write path (stage, then Apply under a `direct` rule) and F2 gave the
rules as data. Neither can run an organisation that is not a solo maintainer: when the rule says
"someone else approves", the tray stays disabled with the sentence "proposals arrive with P2".
P2 is that arrival. It delivers the middle of the loop (architecture §3):

```
 change ──propose──▶ proposal ──rule──▶ decision ──▶ record updated
 (staged)            (events)        (evaluated)    (one merge commit)
```

1. **Propose**: the actor's staged change becomes a proposal under the rule that governs its
   classes (§3.4).
2. **`data/proposals.yaml`**, the ledger: the proposal, its operations, its events, its state (§3.1–3.3).
3. **Branches built by replay**: a `proposal/<id>` branch holding the change, rebuilt from the
   recorded operations whenever the trunk moves under them (§3.5).
4. **Events**: approve, object, vote, retract, comment, withdraw, each with its author (§3.2).
5. **The rule evaluator** for every method: direct, approve, consent (with its window), vote
   (quorum and threshold), system (an outside outcome, read-only) (§3.6, §3.7, §3.11).
6. **Ratify and merge** as one commit whose trailers `validate:governance` accepts, with the
   decision recorded and the `DECISIONS.md` entry appended (§3.8–3.10).
7. **How members on their own machines reach each other's proposals** before hosting exists (§3.12).
8. **The screens**: Propose in the Changes tray, the proposal page, Governance's open list, built
   from P4's parts and skin-neutral (§3.14).

P2 builds on one fact the earlier tracks set up on purpose: everything it needs to *decide* is
already pure and tested (`ruleFor`, `mayPropose`, the `proposal` machine). What P2 adds is the
clock, the event stream, git, and the screens.

## 3. Decisions

### 3.1 The ledger: `data/proposals.yaml`

A collection registry `proposals` (top key `proposals`), written **only by the proposal routes**.
The registry carries `ledger: true`: the change engine refuses to stage an operation on it ("proposals
are changed by their own routes"), and the old `PUT/POST/DELETE /api/registries/proposals` routes
answer the same sentence. A hand edit is not prevented (the data plane stays writable, architecture
§4.7) but is *caught*: §3.10.

```yaml
proposals:
  - id: p-2026-10-18-001-a3f9       # p-<date>-<NNN>-<xxxx> (amended at build): NNN counts that day's proposals, xxxx is 4 random hex
    title: Move one project to develop; add a partner
    rationale: Why this is worth deciding. Plain text.
    author: ana                      # a member id, set by the server from the actor, never from the request
    classes: [records]               # classOf of every op, whole classes (F2-R21: splits stay inert)
    rules:                           # the rules it was opened under, as they stood (ruling P2-R5)
      - { id: records, applies_to: [records], propose: member,
          decide: { by: maintainer, method: approve, count: 1 } }
    state: open                      # open | ratified | rejected | withdrawn | expired
    opened: 2026-10-18T10:02:00-03:00
    rev: 3f9a1c20b7de                # first 12 hex of sha256 over the ops without bases (ruling P2-R7)
    base: 9c1e04a                    # trunk sha the branch was last replayed onto
    branch: proposal/p-2026-10-18-001-a3f9
    ops:                             # the content; the branch is derived from this (ruling P2-R6)
      - { op: update, record: "projects:alpha", set: { stage: develop }, base: 80c3e1198ce9d975e15b545ea6afd1f32a13c75d7f99b7071f3856fd65acecf1 }
      - { op: create, record: "relationships:beta", value: { id: beta, partner: Beta }, base: null }
    statement:                       # optional: present = record as a decision (§3.9)
      title: …
      decision: …
      why: …
      scope: records
    events: []                       # §3.2, append-only
    closed: null                     # set with the closing commit: { at, by, decision }
```

- **`id`** (amended at build, final review I5): the day's counter `NNN`, then 4 lowercase hex drawn from the
  server's random source (drawn again on a clash within the ledger, as event ids are). With the counter alone, two
  members proposing on the same UTC day before either Share was fetched both minted `p-<date>-001`, Sync refused the
  ledger ("both sides opened a proposal with this id"), and no hand fix could pass the validator. The schema and the
  validator still accept the shape before the suffix, `p-<date>-<NNN>`; the server mints only the new one, and its git
  guard builds `refs/heads/proposal/<id>` only for it.
- **`ops`** are P1's `StageOp`s plus `base` (the sha-256 of the entry's canonical YAML when
  staged; null for a create). `before` is not stored: the diff reads it from the branch's parent.
  The example above parses as written, and Task 1's test runs it: `relationships` is a real collection
  registry and `base` a 64-hex sha-256 (the second review's example named `partners`, which has no registry:
  `parseRecord` throws "names no registry", LOW-5 of the third review).
- **`rules`** is the normalised F2 `Rule` list that governed the proposal's classes *when it was
  opened*, one per distinct rule id. Evaluation reads this snapshot, not the file's current rules,
  so a rule change that is ratified while a proposal is open does not change what that proposal
  needed (architecture §4.5: "decided under the rule in force when it was proposed"). `validate:governance`
  checks that the snapshot equals what `ruleFor` gave at the parent commit, so a proposal cannot
  carry a laxer rule than the one in force (§3.10).
- Entries keep their YAML comments and layout: they are written with the same splice
  `applyOps` uses (`updatedText` / `createdText`), with its exact-write check.
- The file is created at the first Propose, with its top key, exactly as a create on a missing
  registry file is today (P1 §7.1 step 8).

### 3.2 Events

An event is one line of data with its author. It is appended to `events` in a commit of its own.

```yaml
events:
  - { id: e-lq3k2-bd, at: 2026-10-18T11:00:00-03:00, by: bruno, kind: approve,  rev: 3f9a1c20b7de }
  - { id: e-lq3m9-ca, at: 2026-10-18T11:20:00-03:00, by: carla, kind: object,   rev: 3f9a1c20b7de,
      text: "This moves the stage before the budget is agreed; that harms the aim." }
  - { id: e-lq3pp-bd, at: …, by: bruno, kind: vote, vote: yes, rev: … }
  - { id: e-…, at: …, by: carla, kind: retract, of: e-lq3m9-ca }
```

| Kind | Who may | Effect on evaluation |
|---|---|---|
| `approve` | a person in the `by` of a rule of the proposal, and not the author unless a rule that names them sets `self_approve`: the one contract below (P2-R2) | counts, for the current `rev`, under `approve` |
| `object` | a person in `by`; **`text` is required** (the argument that the proposal harms the aim, charter principle 6) | blocks `approve` and `consent` until retracted or answered by a revision |
| `vote` | a person in `by`; `vote` is `yes`, `no` or `abstain`; the latest per member counts | counts under `vote` |
| `comment` | any known member, an agent included; `text` required | none. How a non-decider is heard. |
| `retract` | the author of the event it names (`of`) | removes that event from the live set |
| `revise` | the proposal's author (§3.5) | new `rev`; clears approvals; answers objections; restarts the window |
| `replay` | any known actor, or the server; with a `choose` (stale proposals), the author only (amended at build, P2-B38, P2-B50) | none: a mechanical re-base (§3.5) |
| `attach` | any member who may propose, and only when a rule of the proposal's snapshot has method `system` (amended at build, P2-B49) | binds an outside reference for `system` rules (§3.11) |
| `system` | the server only: `by: system:<system id>` | an outside outcome as read (§3.11) |
| `withdraw` · `reject` · `expire` · `ratify` | closing events (§3.8) | written in the same commit that sets the final state |

- **`by` is set by the server** from the resolved actor, never from the request body. An unknown
  actor (no member matches the git identity) cannot write an event.
- **The table above is written once** (LOW-3 of the third review): `eventPermission(kind, { actor,
  proposal, rules, book })` in `lib/proposals.mjs` (Task 1) returns null or the refusing sentence for every
  row (`approve` by the contract below; `object` and `vote` only by a decider; `retract` only of one's own
  event; `revise` and `withdraw` only by the author; `attach` only by a member who may propose, and only when a rule's method is `system`; `system` only
  by the server). `rules` is the proposal's **rule snapshot**, the whole array as the ledger stores it, never
  one rule of it. The machine's guards (Task 4) and the validator (Task 14a-1, which imports only `evaluate`,
  `proposals` and `ops`) both call it, so the page, the route and the check cannot disagree.
- **The `approve` contract (M-B of the fourth review). It is stated here once; §3.3, §3.6, §3.10 and Tasks 1,
  2 and 4 point to it and say nothing different.** Two questions are kept apart, because the snapshot may
  hold several rules (§3.7):
  1. *May this event be written?* (`eventPermission`, so the machine's guard and the validator.) An `approve`
     by `actor` is allowed when `actor` is a person in the `by` of **at least one rule of the snapshot**, and
     either is not the proposal's author, or is the author **and some rule of the snapshot that names them in
     `by` sets `self_approve: true`**. A person in no rule's `by` may not approve at all. Otherwise the
     refusal is the sentence `notAuthor` gives.
  2. *Does it count, and for which rule?* (`evaluate`, §3.6.) An approval counts toward a rule only when its
     writer is in **that rule's** `by` and is either not the proposal's author or that rule sets
     `self_approve`. So the author's approval, once written, counts toward the rules that set the key and name
     them, and not toward the others; the `missing` sentence of a rule that does not count it says "other than
     the author".
  With one rule the two questions have one answer. With rules `[A (self_approve), B]` and the author a decider
  in both, the author's `approve` is written (question 1) and counts toward A only (question 2); B still waits
  for someone else. Task 1's test rows, Task 2's evaluator tests and Task 4's guard test each assert this case.
- **Ids** are `e-<time base36>-<2 hex of a random>`: unique without a counter, so two members
  appending at once cannot collide (§3.12).
- **Order** is `at`, then id. `at` is the server's clock when the event is written. Order is for
  reading and for the evaluator; **the validator does not require a new event to be later than the
  last one** (events from two machines interleave after a Sync, and their clocks differ). It requires
  instead that an event's `at` lies within `CLOCK_SKEW` (`PT10M`, one constant) of the committer date
  of the commit that adds it, and not earlier than the proposal's `opened` minus `CLOCK_SKEW`
  (§3.10, P2-R30). Two events with one id are a finding.
- **A server refuses to write an event that the evaluator would ignore**: a `vote` after the voting
  closed, any event after the proposal's expiry (§3.6 "Pinned cases"). It also refuses when its own
  clock is more than `CLOCK_SKEW` behind the newest `at` in the ledger ("your clock is 3 hours behind
  this proposal's last event; fix it and try again"), so a slow clock cannot back-date a decision.
- **The live set** (what `evaluate` reads): events not named by a later `retract`; for `approve`
  and `vote` only those carrying the proposal's current `rev`; objections whose `rev` is older than
  the current one are *answered* and no longer block (architecture §4.5: "answered by a revision").
  The objector can object again.
- One commit per event: `proposals: approve p-2026-10-18-001`, trailers `Org-Actor`,
  `Org-Proposal`, `Org-Rule` (§3.13). The git log is the audit trail.

### 3.3 The proposal as a P4 machine

P4 defined `proposal` and left it unused; P2 switches it on and amends it. The *stored* state is
the five of architecture §4.4 (`open | ratified | rejected | withdrawn | expired`); the machine's
open sub-states are **derived on read** (as `ChangeState` is) and never stored:

| Derived state | When |
|---|---|
| `stale` | any op's base no longer matches the entry on the trunk (§3.5) |
| `objecting` | open, not stale, and the lead rule's method is `consent` |
| `voting` | … `vote` |
| `approving` | … `approve`, `direct` (P2-R4) or `system` |

The **lead rule** of a proposal with several rules (§3.7) is its most demanding method, in the
order `vote`, `consent`, `system`, `approve`; the sub-state is only a label, the evaluation is
over all of them.

Amendments to the machine (the generated walk test keeps passing; its fixtures move with it):

- New events: `COMMENT`, `RETRACT`, `ATTACH`, `SYSTEM` and `REVISE` as self-loops in the open
  states, so the routes use `transition()` for every event and refuse the same way (`409 refused`
  with the guard's sentence). `REVISE` from `stale` also moves to the derived sub-state.
- New guards: `mayJudge` (the actor holds `by` in a rule of the proposal, is a person),
  `notAuthor` (for `APPROVE`: the first question of the contract in §3.2; it refuses the author unless a rule of the snapshot that names them sets `self_approve`), `pastDue` (for `EXPIRE`; today any actor could expire), and
  `mayRatify` (§3.8). `ruleMet` / `ruleFailed` read `context.outcome` from `evaluate`, as P4 intended.
- `REJECT` is available only when an evaluation says `failed`. Under `approve` and `consent` a rule
  cannot fail, only wait (P2-R9); `vote` and `system` can.

### 3.4 Propose

*Propose* takes the actor's open change (the tray) and turns it into a proposal.

1. **Which rules.** `rulesForClasses(effectiveRules(governance).rules, classesOf(ops))`. A class
   with no rule is uncovered: refused ("no rule covers the class treasury; nobody can propose it
   until a rule does"). For each rule, `mayPropose(rule, actor, book)` must be `true`; the first
   refusal sentence is the answer (403).
2. **The method decides whether a proposal is needed.** If the actor may apply every class alone
   (`mayDecideAlone`), nothing opens: the tray offers *Apply*, as today (architecture §3). *Propose*
   is offered only when `direct` is false.
3. **No stale ops** (409, as Apply), and the ops validate against the entries as they would be
   (`validateChange`, 422 with field errors). Opening is refused while the trunk is dirty in
   `data/proposals.yaml` or the repository is off the trunk (P2-R17).
4. **One commit on the trunk**: the new entry, `state: open`, in `data/proposals.yaml`, trailers
   `Org-Actor`, `Org-Change` (the change's id), `Org-Proposal`, `Org-Rule`.
5. **Then the branch** (§3.5). A failure to build it does **not** undo the commit: the branch is
   derived, and is built again when first needed. The response says so (P2-R25).
6. **Then the change is cleared**, exactly as after Apply. The ops now live in the ledger.

A change marked `revises` is not a new proposal and is not an Apply: Propose (`POST /api/proposals`) and Apply both refuse it on the server with 409, "This change revises proposal <id>: press Update proposal, or discard it first. Nothing was written." (amended at build, P2-B57). A proposal never forks (P2-R23).

**Revising.** An author whose open proposal needs changes does not open a second one. *Revise* loads
the proposal's ops into the author's tray (refused if the tray holds a different change: "apply,
propose or discard it first"), marks the change `revises: <id>`, and the tray's primary action
becomes *Update proposal*, which writes a `revise` event with the new ops and `rev` (P2-R23).

### 3.5 The branch, by replay; staying current

**The branch is a cache of the ledger, not the other way round** (P2-R6). The ops in
`proposals.yaml` are the content; `proposal/<id>` is built from them, locally, whenever it is needed
(Propose, the diff view, ratify). It is **never pushed by the platform** (§3.12), so a member on
another machine rebuilds it by replaying the same ops, and gets the same tree. Rejected, withdrawn
and expired proposals keep their branch (architecture §4.4); the platform never deletes one.

**The invariant (H1).** *The branch tip is one commit whose first parent is a trunk commit and
whose tree is that parent's tree plus the proposal's ops, and nothing else.* A ratify merge can then
only bring the proposal's own operations onto the trunk, because git reads a merge as "what the
branch changed since the common ancestor", and the common ancestor is the branch's own parent. The
first draft broke this: it brought the trunk's tip into the branch with `merge -s ours`, which keeps
the branch's *old* tree, so the later merge into the trunk read every trunk change since the old
base as something the branch had removed (reproduced by the reviewer; see the report's proof A). **Replay
never merges.** It builds the commit again.

**Building and replaying are one function** (`buildBranch(repo, proposal, from)`), plain git and `applyOps`:

1. `git worktree add --detach <state dir>/proposals/<id>-<n> <from>`, a fresh, detached worktree under
   the admin state directory, outside the repository. `<from>` is the trunk tip (`T`). `<n>` is a
   counter, so a worktree left behind by a failed build never blocks the next one.
2. `applyOps(<worktree path>, ops, { message, trailers })`: P1's apply, pointed at the worktree. It
   validates against the worktree's entries, writes, and commits once with `Org-Actor: <author>`,
   `Org-Change`, `Org-Proposal`. The commit is `C`, and `C^` is `T`.
3. `git rev-parse HEAD` in the worktree gives `C`; `git worktree remove <path>` (no force: it refuses a
   dirty worktree and the failure leaves the path in the message for a person to look at).
4. `git update-ref refs/heads/proposal/<id> C <old>`, where `<old>` is the branch's current tip, or
   forty zeros when the branch must not exist yet. This is a compare-and-swap: if anyone moved the branch in
   the meantime the command fails and nothing moves (proof C). The platform names no other ref in
   `update-ref`: the function builds `refs/heads/proposal/` + a validated proposal id itself and
   takes no ref from a caller.

**Idempotent (LOW-7; LOW-1 of the third review).** A rebuild makes a new commit each time (its date
differs), so "calling it twice is safe" needs a rule the code can run. The second review's rule compared the tip's
tree with "`from`'s tree plus the ops" "without building", and that tree is not known without applying the ops,
which needs the worktree. So `buildBranch` **always builds** in its detached worktree (steps 1 to 3) and
**compares tree ids before step 4**: if `proposal/<id>` exists, its tip's first parent equals `from`, and the tip's
tree id equals the new commit's tree id, it **does not move the ref** (step 4 is skipped), has already removed
the worktree, and returns the existing tip. The new commit is left unreferenced in the object store, where git's
garbage collection removes it; no branch, ref or worktree is left behind. Otherwise step 4 moves the ref.
Proof ID (git 2.43): two builds from one `from` gave two commits with the same tree id; the ref stayed on the
first, the worktree list showed the main worktree only, no ref named the second commit, and a different result
(`a: 3` for `a: 2`) gave a different tree id.

The old tip is not kept by the platform (it stays in the repository's reflog like any moved ref); the
ledger holds the ops, which is the content (P2-R6), and a `replay` event records the new `base`.

**Current with the trunk.** A proposal is *stale* when an op's `base` no longer matches the
entry on the trunk (`staleOps`): not whenever the trunk moves. Event commits touch only
`proposals.yaml`, which no op names, so a busy proposal does not keep going stale. Three cases:

- **No op's entry changed.** Nothing to do for the *proposal*. The branch may be behind the trunk;
  it is rebuilt when it is needed (below), never merged forward.
- **An op's entry changed.** The proposal is `stale`. The author resolves it with the tray's own
  choices per op: *Keep mine* re-bases the op (a `replay` event, `rev` unchanged: approvals stand; **if re-basing changes the ops, so that their `rev` differs, it writes a `revise` event with the new `rev` instead and approvals on the old `rev` stop counting**: amended at build, P2-B37);
  *Take theirs* drops its conflicting fields (a `revise` event: `rev` changes, approvals clear).
  Until then no event except `comment`, `retract` and `withdraw` is accepted (the machine's `stale`
  state has no `APPROVE`).
- **Replay** (mechanical, any known actor): `buildBranch`
  again from the trunk tip. A `replay` event records the new `base`. (Amended at build, P2-B50: the proposal machine has a `REPLAYED` self-loop in the open states, guarded by `mayWrite`, for a non-stale proposal whose branch is behind the trunk; it writes nothing when nothing moved. Amended at build, final review I4: each replay writes an event, which moves the trunk, so "behind the trunk" is never a fixed point; a mechanical replay (no `choose`) is offered and acts only when the trunk changed one of the files the ops name since the proposal's `base` (`git diff-tree -r --name-only <base> <tip>` against the ops' files: the machine's `trunkMoved` guard); otherwise `can` does not offer it and the route answers "Already on the trunk: nothing to replay." without writing. In `stale`, `REPLAYED` needs a `choose` (*Keep mine* or *Take theirs*) and the author (P2-B38). Ratify does not replay: it rebuilds the branch inside its preflight and writes no event.)

**An outdated branch (amended at build, P2-B52, P2-B53).** A branch whose tip was built from an older `rev` than the proposal's is outdated. It is detected by the `rev` written into the branch commit's message ("Built from rev <rev> of the proposal's ops.", read back with `log -1 --format=%B`), not by commit dates. The page's diff rebuilds it as it would a missing one, and `branchState` reads `missing` until it is rebuilt; the check is repeated inside the write lock before building.

**When the branch is rebuilt.** On Propose; on a replay; and **by ratify, whenever the branch tip's
first parent is not the trunk tip** (`git rev-parse proposal/<id>^` is compared with `T`). After that
the merge is between `T` and a commit whose parent is `T`: there is nothing for git to merge and no
textual conflict is possible, even when the trunk edited another entry of the file an op edits
(proof F; without the rebuild, git conflicts there). Ratify rebuilds *inside* its own preflight, before any file of the
working tree is touched (§3.8), and refuses if the branch's content commit changes a path outside the
files the ops name (`git diff --name-only T C`, which a rebuilt branch cannot fail and a hand-made one can).

**Rev.** `rev` is the first 12 hex of the sha-256 of the canonical JSON of the ops *without* `base`
and `before`. Re-basing never changes it; editing the content always does.

### 3.6 The evaluator

`packages/admin/lib/evaluate.mjs`: plain ESM, JSDoc, **no I/O and no `node:*` import**, so the
client bundles the same function the server and the validator run.

```js
evaluate({ rule, proposal, book, now }) → Evaluation
//  rule     a normalised F2 Rule (from proposal.rules)
//  proposal { author, opened, rev, events, ttl? }   — plain data
//    (amended at build: `ttl` is read by the evaluator but the ledger schema has no such key and nothing writes one in P2, so the expiry is the rule's `expires`, else P30D)
//  book     resolveRoles(governance, members), roles as of now (P2-R5)
//  now      a Date or ms; the only clock there is
Evaluation = {
  state: 'pending' | 'met' | 'failed' | 'expired',
  missing: string,        // the sentence shown: "needs 1 more approval from a maintainer other than the author"
  tally: { for?: string[], against?: string[], abstain?: string[], objecting?: string[], needed?: number },
  closesAt: string | null // ISO: when a window or the expiry ends the evaluation by itself
}
evaluateAll({ proposal, book, now }) → { state, missing, parts: { rule, evaluation }[], closesAt }
```

Terms: **deciders** = the members `book` resolves for `decide.by`, persons only (F2 already refuses
agents there). **Since** = the later of `opened` and the latest `revise` event's `at`. **Live**
events are §3.2's.

| Method | `met` when | `failed` when | `expired` when | `missing` says |
|---|---|---|---|---|
| `direct` | treated as `approve` with `count: 1` (P2-R4). A `direct` rule can only reach a proposal when the author is outside `by`; any one decider's approval is the decision. | never | by TTL | as approve |
| `approve` | ≥ `count` live approvals from deciders other than the author (the author's counts under a rule with `self_approve: true`), and no live objection from a decider | never (an objection waits, P2-R9) | by TTL | "needs 2 more approvals from a maintainer other than the author" · "held open by an objection from a maintainer: answer it with a revision, or ask them to withdraw it" |
| `consent` | `now ≥ since + window` and no live objection from a decider | never (an objection holds it open, architecture §4.5) | by TTL | "the objection window closes in 2 days 3 hours" · "held open by an objection from …" |
| `vote` | the vote has **closed** (below) and quorum is reached (members who cast `yes`, `no` or `abstain`) and `yes / (yes + no) ≥ threshold`, the share being **0 when `yes + no` is 0** | the vote has closed, quorum is reached, and the share is below `threshold` (an all-abstain vote is here: nobody affirmed) | the vote closed without quorum (P2-R10) | "voting closes in 4 days; 2 of 3 have voted, quorum is 2" |
| `system` | the latest `system` event reads `executed` (§3.11) | the latest reads `failed` | by TTL | "waiting for the Safe: no transaction attached yet" · "transaction 0x…: 1 of 2 signatures" |

- **Comparisons** are the ones F2-R16 fixed: `≥ count`, `≥ quorum`, `≥ threshold` of the share.
  An abstention counts toward quorum and not toward the share (P2-R10).
- **The author may vote and may consent**; the four-eyes rule (P2-R2) is only for `approve`,
  because a vote's weight is the group's, and an approval is a review.
- **`self_approve` (M-4 of the third review).** A rule may say `self_approve: true`, an optional boolean key
  of F2's rule vocabulary beside `expires`; default false, which is four eyes. Task 2 builds it, not only the
  default: the key is added to `RULE_KEYS` (today `lib/rules.mjs` makes any other key an error), to
  `governance.schema.json`, to `describeRule` ("the author's own approval counts") and to the evaluator, with a
  test for each value. `normalise` keeps the key only when it is true, so a snapshot of a rule without it
  equals what `ruleFor` gave and §3.10's equality check holds for both. With several rules the contract of
  §3.2 applies: the guard (Task 4) lets the author's `APPROVE` through when a rule of the snapshot that names
  them sets the key, and the evaluator counts it toward the rules that set it and not toward the others. Question 1 is therefore the choice of the default shipped, one value, not a change of code.
- **TTL.** A proposal with no decision `P30D` after `since` is `expired` (P2-R11). A rule may
  say `expires: P14D` (F2's rule vocabulary gains this one optional key for every method; `checkGovernance`
  validates it as a duration). `consent` and `vote` end at their window, so `expires` matters most
  for `approve` and `system`.
- **A vote that has not closed is `pending`**, even when the count already settles it: nobody is
  told "passed" before the window the rule promised has ended (unless everyone has voted).
  **Closed** has one definition, `closedAt`: the earlier of the window's end (`since + window`) and
  the `at` of the event after which every decider holds a live vote, found by taking the events in
  order. A `vote` event with `at ≥ closedAt` is not counted, and the server refuses to write one.
- **Purity.** `evaluate` never reads the clock itself. The server passes `new Date()`; every test
  passes a fixed date. The window boundary is `now ≥ since + window` (inclusive), pinned by a test.
  The ratify merge is evaluated at the whole-second floor of the server's clock and committed with git's own date, so the merge's date is within `CLOCK_SKEW` of that evaluation's now and at or after the floor (amended at build, P2-B18; R30).
- **Every sentence is built here**, so the page, the tray, the machine's guard and the validator
  speak with one voice.

**Pinned cases (M7).** Each is a row in `evaluate.test.ts` that fails on the other reading.

| Case | The reading | Why |
|---|---|---|
| `vote`, quorum reached, every ballot `abstain` (or `yes + no = 0`) | `failed`, `missing`: "nobody voted for or against" | the share is 0, below any threshold above 0 (`checkGovernance` already requires `0 < threshold ≤ 1`, `lib/rules.mjs` line 417). Waiting until the TTL would hide a decided outcome |
| `vote` cast with `at ≥ closedAt` | not counted | an outcome must not flip after it was announced; the server also refuses it |
| a rule `met` and also past its expiry | the events with `at` **before** the expiry instant (`since + ttl`) are evaluated; if that is `met`, the answer is `met` and stays ratifiable; otherwise, if `now ≥` the expiry instant, `expired`. Events at or after the expiry instant do not count | expiry must not revoke a decision the people reached in time, and must not let a late event rescue or block one |
| `approve` where `count` exceeds the eligible approvers (deciders other than the author, under four eyes, P2-R2; every decider when the rule sets `self_approve`) | `pending` with `blocked: 'unmeetable'` and `missing`: "cannot be met: only 1 maintainer other than the author, and the rule asks for 2. Withdraw it, or change the rule". `checkGovernance` **warns** when the rule does not set `self_approve`, `count ≥ number of deciders` **and every member who may propose under the rule is also a decider** (`propose ⊆ by`: then the author is always a decider, so four eyes can never be satisfied; if someone outside `by` may propose, the rule works for them and no warning is certain: LOW-4, the evaluator's own sentence covers the proposals that deadlock); it stays an error only for `count >` the number of deciders (F2's check) | a two-person coop or a solo maintainer with a written rule would otherwise get a proposal nobody can approve and no sentence saying so |
| `threshold` and abstention | the share is `yes / (yes + no)`; abstentions count for quorum only | F2 and the architecture say "of the votes cast" without ruling on abstention; P2-R10 reads it so, and a test pins it |
| an `object` from a non-decider | a comment; does not block | P2-R9 |
| the author votes or consents | counts | only `approve` excludes the author |
| `direct` reaching a proposal | `approve` with `count: 1` | P2-R4 |

### 3.7 Several classes: one proposal, every rule must be met

A change that touches classes governed by different rules (for example a project and a member)
gets **one proposal whose `rules` lists each distinct rule, and it is decided when every one of them
is `met`** (P2-R1, the conjunction). Reasons:

- It keeps the change atomic: a project moved *and* the partner who works on it added, or neither.
  The alternative, a proposal per rule, splits it into two decisions that can disagree.
- "The strictest rule" has no order: `approve` by maintainers is neither stricter nor laxer than
  `consent` by members. A conjunction needs no order.
- The cost is that the slowest rule sets the pace. The page shows each rule's own status, so the
  reader sees which one is holding it.

One event counts toward every rule where the actor is a decider (a maintainer's approval satisfies
the `records` rule and the `members` rule if both name `maintainer`). `failed` in any rule fails the
proposal; `expired` in any rule expires it. The `proposal.rules` snapshot has one entry per rule id.

### 3.8 Ratify, and the other ways a proposal closes

**Ratify is an act of a person, never of the clock** (P2-R3). When `evaluateAll` says `met`, the
page says "Ready to ratify" and the clock stops mattering; nothing is written until a person presses
*Ratify*. The same holds for *Close as rejected* (when `failed`) and *Close as expired*. This keeps
the decision with people (charter principle 12): the rule says *what is enough*, and a person
carries it out. The actor who may ratify is the author or any decider of the proposal's rules, a
person (an agent never ratifies, architecture §4.2); the machine's `mayRatify` guard says so.

**Ratify is one merge commit, and it is written in two halves: everything that can be checked is
checked and computed in memory first; the working tree is touched only after that, and every file
touched is staged the moment it is written (H2).** The server, inside the repository's write lock:

*Before anything in the repository changes (steps 1 to 4 write nothing to the tree, the index or HEAD):*

1. **Preflight.** Refuse, in words, unless: no tracked file has uncommitted changes
   (`git status --porcelain --untracked-files=no` is empty); **no merge is in progress** (the file
   `git rev-parse --git-path MERGE_HEAD` names does not exist: LOW-2, below); HEAD is the trunk (P2-R17);
   the three files ratify will write (`data/proposals.yaml`, `data/governance.yaml`, and `DECISIONS.md` when the
   proposal has a `statement`) are **tracked and not hidden** (`git ls-files --error-unmatch`, and
   the `assume-unchanged` / `skip-worktree` check P1 already has), because `merge --abort` cannot
   restore a file git does not track (proof 7); when a remote exists, the last fetch is recent and
   shows nothing new (§3.12); the server's clock is not behind the ledger (§3.2). It re-reads the
   ledger and **re-evaluates** with the server's clock, **floored to the whole second** (LOW-5, below);
   the client's word counts for nothing.
2. **Rebuild the branch if needed** (§3.5): if `proposal/<id>^` is not the trunk tip `T`, `buildBranch`
   from `T`. This writes objects and moves `refs/heads/proposal/<id>` by compare-and-swap and
   nothing else; the working tree, the index and the trunk are untouched. Then check
   `git merge-base --is-ancestor <C> <T>`: if it is true the change is already in the trunk, and
   ratify refuses with "this change is already in the trunk; there is nothing to merge". Without this
   check `git merge --no-ff` answers "Already up to date" and exits 0 with no merge in progress
   (proof 6), after which `merge --abort` itself fails with "There is no merge to abort".
   **After this step `C^` is `T`** (read once more, `rev-parse proposal/<id>^`, and compared; a
   difference is a refusal). That fact is what step 3 stands on.
3. **Compute the three new texts in memory from the tree-to-be, never from `HEAD` (N1).** The tree-to-be
   is `C`'s tree: `C`'s first parent is `T` and its tree is `T`'s plus the ops, so `merge --no-ff` of `C`
   into `T` produces exactly `C`'s tree. The bytes are `git show <C>:<file>`: `data/proposals.yaml`
   (state `ratified`, a `ratify` event, `closed`), `data/governance.yaml` with the decision row (§3.9)
   and, when there is a `statement`, `DECISIONS.md` with the entry. Each is a text splice that keeps
   every other byte. **Why not `HEAD`:** the merge writes the ops' change into the working tree, and a file
   that an op edits can be one of these three. The second draft spliced the decision row into
   `git show HEAD:data/governance.yaml`, which lacks the op; step 6 then overwrote the merged file with
   that text and the commit recorded the ratification **without the change it ratified**, with the change
   still in the second parent (proof N1.A). From `C`'s blob the commit holds both (proof N1.B), also when
   the trunk moved after the proposal opened and the branch was rebuilt first (proof N1.C).
   **Reachability, said plainly.** The re-review's trigger was a rule or role change (class `governance`,
   an op on `data/governance.yaml`). P1's change engine stages only *collection* registries: a record
   naming a document registry such as `governance` is refused ("it is not edited entry by entry, so it
   cannot be staged here", `parseRecord`, read 2026-10-18). So **no op can edit `governance.yaml` today**
   and the loss cannot happen through the tray; it happens the day the engine learns document edits
   (§6, question 13), and nothing in ratify should have to change when it does. The design is therefore
   written to be correct for *any* file an op edits, and Task 11a tests it at the git layer with a branch
   built by hand.
4. **Validate every new text whole** (the `applyOps` discipline: re-parse, shape-check, compare with
   the tree-to-be's text plus the change, run `validateRepo` over a scratch copy of the tree-to-be). A refusal
   here (an unreadable `DECISIONS.md`, a flow-style governance file, a row that would not parse back)
   leaves **nothing** to undo: the repository is as it was, because nothing had been written. This
   is where the "a failed ratify leaves the trunk as it was" guarantee mostly comes from.

*Then the repository is touched, in five small steps, and each says what comes back:*

5. `git merge --no-ff --no-commit proposal/<id>`. Afterwards the server checks that the file
   `git rev-parse --git-path MERGE_HEAD` names exists (a file test, not `rev-parse --verify MERGE_HEAD`,
   which a branch called `MERGE_HEAD` answers present with no merge: proof L2). If it does not (git said
   "Already up to date", which step 2 should have caught), ratify stops with that sentence and runs
   **nothing else**, in particular not `merge --abort`. If the merge failed or left conflicts (it cannot
   after step 2, since the branch's parent is `T`, but the check stays), `merge --abort` is the undo.
   Then two reads, no git command: (a) for each of the three files, the working tree's bytes must equal
   `git show <C>:<file>` (proof N1.B asserts it; a machine that converts line endings fails the check and
   ratify aborts in words rather than guess); (b) **those bytes are the rollback bytes** for step 6,
   held in memory. They are what the merge left in the working tree and the index, which is what
   `merge --abort` compares against.
6. For each of the three files in turn: write the new bytes, then **immediately `git add <that
   file>`** by name. If a write or an add throws, the server first writes the **rollback bytes of step 5**
   back to every file it has written, **and stages each of those files again with `git add`**, then runs
   `merge --abort`. **Not `HEAD`'s bytes (N2):** for a file the merge also changed (`governance.yaml` in a
   `governance` proposal; any file an op edits) `HEAD`'s bytes differ from the index, and `merge --abort`
   then refuses with `Entry '…' not uptodate. Cannot merge.` and leaves a pending merge and `MM <file>`
   (proof N2.A); with the step-5 bytes it works (proof N2.B), also when the failed write had been staged
   (proof N2.C). **LOW-6 of the third review, run on a throwaway (git 2.43, proofs N2.U and N2.S):** `HEAD`'s bytes
   written back and then *staged* let the abort succeed as well (exit 0, empty status); the refusal needs `HEAD`'s
   bytes left *unstaged* (exit 128, `MM gov.yaml`). The step-5 bytes are chosen because they work whether or not the
   re-add succeeds, and the negative control of Task 11a must write `HEAD`'s bytes and not stage them, or it passes
   and proves nothing. For a file the merge did not change the two sets are the same bytes. Staging each file at once is
   what makes the abort restore it: `merge --abort` keeps unstaged edits (proof 2) and restores staged
   ones (proof 3). If the re-add itself throws, the bytes are still back and the index still holds the
   merge's own text, which the abort accepts (proof N2.B); if even that fails the server reports git's
   words and stops.
7. Check the staged set: `git diff --cached --name-only --no-renames` (the flag is added at build, so a rename cannot shorten the set: P2-B8) must be a subset of {the files the ops name,
   the three ledger files}, with no unmerged entry. Anything else is an abort.
8. `git commit` the merge with the message and trailers below, through `commitMerge(repo, message,
   allowedPaths)` (§3.15). A hook that refuses the commit leaves the merge pending with every file
   staged; the server runs `merge --abort` (proof 5).

**What is restored after each step, and how** (every row has a test, Task 11a):

| Failure at | State before | What comes back, and how |
|---|---|---|
| 1 preflight | untouched | nothing to restore; a sentence says what to do |
| 2 rebuild or `is-ancestor` | untouched, but the branch ref may have moved | the working tree, index and HEAD never changed; the ref moved by compare-and-swap or not at all; the branch is a cache, rebuilt next time |
| 3, 4 compute or validate | untouched | nothing: no byte was written |
| 5 merge | clean tree, pending merge or none | `merge --abort` if the `MERGE_HEAD` file exists; if it does not ("Already up to date") there is nothing to undo and nothing is run; a working file that differs from `C`'s blob is an abort |
| 6 write or add | pending merge; some files written | the server writes back the step-5 bytes of every file it wrote, stages them again, then `merge --abort`; files already staged are restored by the abort. **This holds for a file the merge also changed** (N2) |
| 7 staged-set check | pending merge, all files staged | `merge --abort` |
| 8 commit refused | pending merge, all staged | `merge --abort` |
| after 8 | the merge commit exists | nothing is undone; it is a commit. A later problem is reported, never "fixed" with a second commit that rewrites it |

After every abort the server verifies the result and says so: `git status --porcelain
--untracked-files=no` is empty, HEAD equals `T`, the `MERGE_HEAD` file is absent. If the verification fails
(it should not), ratify reports exactly what git says and stops; it runs no other command to repair.
There is still no reset, clean or stash; `merge --abort` is the platform's only undo (P2-R15).

**Time (LOW-5).** Git stamps a commit with whole seconds (proof L5), while a consent window and `closedAt` are
instants in milliseconds. A ratify evaluated at `12:00:00.700` against a window ending at `12:00:00.500`
would be committed with the date `12:00:00`, and the validator, which evaluates at the commit's date,
would say the window had not closed. The server therefore evaluates at **the whole-second floor of its
clock** (`12:00:00.000`): the rule is met only if it is met at that second, and git's date is that second
or later, so the validator's answer is `met` too (a `met` rule stays `met` as time passes, §3.6). The
cost is that a ratify attempted in the last fraction of a second of a window is refused with "closes in
1 second". The commit keeps git's own committer date (setting it needs an environment variable, which the git module's guard forbids): within `CLOCK_SKEW` of the evaluation's now, at or after the floor (amended at build, P2-B18).

*An alternative with no undo at all* (offered to the operator in §5 question 4): build the merge
commit with plumbing (`read-tree` into a temporary index file, `hash-object -w` and `update-index`
for the three files, `write-tree`, `commit-tree -p T -p C`) and move the trunk with
`git merge --ff-only <that commit>`. Nothing in the working tree changes until a finished commit
exists, so a failure before the last step leaves the tree untouched and there is nothing to abort
(proof 8). It trades one undo for a longer, less familiar vocabulary; the recommendation stays
`merge --no-commit` with the table above, because a person reading the repository's history sees an
ordinary merge either way and the shorter vocabulary is easier to guard. (Both N1 and N2 are
consequences of splicing into a working tree the merge has already written; the plumbing path computes
from `C` and writes nothing until the end, so it has neither.)

```
proposals: ratify p-2026-10-18-001 — Move one project to develop

Org-Actor: bruno
Org-Rule: records/approve
Org-Proposal: p-2026-10-18-001
Org-Decision: gov-20261018-001
```

The merge commit's first parent is the trunk's old tip, so `validate:governance`, which walks the
first-parent line, sees the ratification as the one change F2 designed it to see, with a trailer
that §3.10 can check against the ledger *in that same commit*. Because the branch tip's parent is
the trunk's old tip (§3.5), the merge changes exactly the files the ops name plus the ledger files;
a test hashes every other tracked file before and after (proof B).

**The other closings** are single commits on the trunk, with no merge:

| Closing | Needs | Writes |
|---|---|---|
| `withdraw` | the author, state open | state `withdrawn`, a `withdraw` event, `closed`. No decision row: nobody decided. |
| `reject` | `evaluateAll` says `failed` | state `rejected`, a `reject` event, `closed`, a decision row `outcome: rejected` |
| `expire` | `evaluateAll` says `expired` | state `expired`, an `expire` event, `closed`, a decision row `outcome: expired` |

All three keep the branch. Their commits touch `proposals.yaml` and (for reject and expire)
`governance.yaml`'s `decisions[]`; both are *ledger* files (§3.10). They follow the same two halves
as ratify, without the merge: preflight (including that the files are tracked), compute and validate
the new texts in memory, then for each file write and `git add <file>` at once, then `git commit`.
With no merge the tree-to-be is `HEAD`'s tree, so here (and only here) the texts come from
`git show HEAD:<file>`, and no op can have changed these files. There is no merge in progress and so
no `merge --abort`: a failure after the first write puts the original bytes back (the working tree's,
read in preflight, which equal `HEAD`'s because the tree was clean) and stages the file again with
`git add` of those same bytes, so the tree is as it was; a test hashes every tracked file before and after a forced failure at each
point.

**What ratify does not do:** it does not run `generate:schemas`. The architecture says "`generate:schemas`
runs", but `.well-known/**` is class `identity` in F1's table, so a regeneration inside the merge
would make every ratification touch a governed class the proposal never named (P2-R20). After a
ratify that changed what `.well-known/` is generated from, the Governance page raises one line,
"Generated files are behind the data: run npm run generate:schemas and commit .well-known/." (amended at build, P2-B60).
**There is no regeneration operation in P2 and the line has no button** (the operator's q6, §5 question 6): the person
runs the script and commits. The line comes from `GET /api/generated` (§3.15): behind when the newest ratify merge
(a commit with both `Org-Proposal` and `Org-Decision`) on the trunk's **first-parent** line that changed `data/`,
`federation.yaml`, `content/projects/` or `content/meetings/` is newer than the newest commit that changed
`.well-known/`; it reads local history only, newest 500 first-parent commits. What it does not see: a ratify that
a divergent Sync brings in below the second parent, because the merge itself, not the ratify beneath it, is on the
first-parent line. It counts a reject or an expiry that changed those paths too. The server memoises the answer by the head sha (P2-B62).

### 3.9 The decision record and the `DECISIONS.md` append

**A row in `governance.yaml` `decisions[]` for every decided proposal** (ratified, rejected, expired;
not withdrawn), as architecture §4.6 and F2 §3.11 shape it:

```yaml
decisions:
  - id: gov-20261018-001           # gov-<date>-<NNN>, NNN counted among that day's rows
    proposal: p-2026-10-18-001
    rule: records                  # the rule ids, comma-joined when several
    method: approve                # the lead rule's method
    outcome: ratified              # ratified | rejected | expired
    status: ratified               # equal to the outcome (amended at build, P2-B14): governance.schema.json requires it
    by: [bruno]                    # who affirmed: live approvers and yes-voters; [] under silent consent
    date: 2026-10-18
    title: Move one project to develop
    summary: 1 approval (bruno); no objection.   # generated from the evaluation's tally
```

A `direct` apply of class `records` creates no row (architecture §4.6). The file is edited as
**text**, as F2's migration does: the row is inserted inside the `governance:` block's `decisions:`
list (turning `decisions: []` into a block list when it is empty), every other byte, comment and
line ending kept, and the result re-parsed and compared with the original plus the row; if it differs
nothing is written. A governance file the inserter cannot edit safely (flow style, no wrapper)
refuses the ratification in words and names the row to add by hand.

**`DECISIONS.md`** gets an entry when the proposal carries a `statement` (the *Propose* form
requires one for classes `governance` and `identity`, architecture §4.6). The entry is built in the
instance's own convention, read from the file itself:

- The next id continues the newest heading's scheme: for `## 2026-10-16 · LD-2026-035 — …` the next
  is `LD-2026-036`; if the newest heading has no id, the heading is `## <date> — <title>`.
- It is inserted as the newest section, directly after the Conventions block's closing `---`.
- Body: `**Status:** active` · `**Scope:** <statement.scope>` · `**Decision** — <statement.decision>` ·
  `**Why** — <statement.why>` · `**Refs** — the proposal id, the decision row id, the merge commit's
  short sha is **not** written (it does not exist yet; the trailers carry it).
- A file whose structure the inserter cannot recognise (no `---`, no convention) refuses the ratify
  and says what to add; it never guesses.

Both the row and the entry point at the proposal (`proposal: p-…`, `Refs`), so the trail reads from
either end.

### 3.10 `validate:governance` closes the loop

F2 left two holes on purpose: a trailer is accepted by presence (F2-R8), and `proposals.yaml` is
exempt from judgement (F2-R13). P2 closes both with one idea: **the ledger is judged by its own
check** (P2-R13), instead of being exempted or being governed like a record.

**The ledger files** are `data/proposals.yaml` and `governance.yaml`'s `decisions[]` (deep-compare
the document without `decisions`: if only `decisions` changed, the commit's change to
`governance.yaml` is a ledger change; otherwise it is also a change of class `governance`). For every
commit, first-parent, that touches a ledger file, relative to its parent:

| Change | Allowed only if |
|---|---|
| a new proposal | state `open`; `opened` within `CLOCK_SKEW` of the commit's committer date; `author` is the commit's actor (the member `findMemberByEmail` finds) and holds the rule's `propose`; `rules` equals `ruleFor(<parent's rules>, class)` for every class in `classes`; `classes` covers `classOf` of every op; an `Org-Proposal` trailer names it |
| new events on an open proposal | each event's `by` is the commit's actor; the kind is allowed for that actor (§3.2's table: `approve`, `object`, `vote` only for a decider; `approve` by the contract of §3.2, the author's only when a rule of the snapshot that names them sets `self_approve`; `retract` only of one's own; all through `eventPermission`, §3.2); `rev` matches the proposal's; the event id is new; `at` is within `CLOCK_SKEW` of the commit's committer date and not before the proposal's `opened` minus `CLOCK_SKEW` (no ordering against other events: P2-R30); a `vote` is not at or after the vote's `closedAt`; `Org-Proposal` names the proposal |
| `ops`/`rev` changed | a `revise` event by the author in the same commit |
| state → `ratified` | the commit is a **merge**; its `Org-Proposal` names this proposal; in the commit's own tree the proposal is `ratified`, in its parent `open`; `evaluateAll` over the commit's tree, with the commit's date as `now` and the roles of the parent, says `met`; the actor may ratify; a decision row for it is present; **and the content is the proposal's own (M4):** the merge's second parent has the merge's first parent as its own first parent, the files the merge changes against its first parent are a subset of {the files the proposal's ops name, the ledger files, `DECISIONS.md`}, and for every op the record in the merge's tree equals the op's result, computed by `projectOp` from **`lib/ops.mjs`** (moved there from `server/changes/records.ts` in Task 3b, so the root validator and the server run one function and cannot drift; `yaml` and `lib/registries.mjs` are already `lib` dependencies) (a `set` op: the named fields hold the new values; a `create`: the entry equals the value; a `delete`: the entry is gone) with every other record of those files equal to the parent's, compared as parsed data (not text layout) |
| state → `rejected` / `expired` | `evaluateAll` says `failed` / `expired`; the decision row is present |
| state → `withdrawn` | the actor is the author; the proposal was open |
| a closed proposal changes, or a proposal disappears | never |
| a decision row | only with a closing commit of the proposal it names, and equal to what the evaluation produces (`outcome`, `method`, `by`) |

A finding says the commit, the proposal and the sentence. With this:

- **A merge carrying `Org-Proposal` ratifies exactly that proposal** (amended at build, P2-B39): open at the merge's first parent, `ratified` in the merge, no other proposal changed. A trailer naming a proposal the ledger does not change, or a merge that ratifies another, is a finding; the trailer is otherwise a bypass.
- **F2-R8's note goes away.** Once `proposals.yaml` exists, `Org-Proposal` is looked up in the
  commit's own tree, must be `ratified` there and `open` at the parent. A later commit cannot
  borrow a proposal already ratified; a forged trailer names nothing.
- A proposal ratified while its `statement` classes demanded a `DECISIONS.md` entry but none was
  appended is a finding.
- **Merge commits that are not a ratification are expanded, and the walk follows the trunk line
  (H3).** The history is still read first-parent, oldest to newest. A merge commit `M` (parents `P1`,
  `P2`) is handled by what it carries:
  - **`M` carries `Org-Proposal`** and the ledger shows it as the proposal's ratification: it is judged
    as **one unit** by the `ratified` row above. The commits beneath its second parent (the branch's
    content commit) are never visited: the row already checks that content.
  - **`M` carries no `Org-Proposal`** (a `Sync` merge, a crew branch landing): it is not judged as a
    change of its own. (Amended at build, P2-B45, P2-B46: the expansion is opened when **any** parent has written rules, each incoming commit being judged by its own parent's gate; it is bounded by `--range`, whose excluded ends are resolved once and appended to every expansion's `rev-list`, nested ones too.) The validator judges the commits **on the second parent's first-parent line
    down to the merge base**: `git rev-list --first-parent --reverse P1..P2`. Each is judged by these
    same rules, and if one of them is itself a merge it is handled by this paragraph again
    (recursively). A commit already judged is not judged twice (a set of hashes).
  - **Why first-parent and not `--no-merges`.** The first draft expanded to the non-merge commits
    `P1..P2`. In the main multi-machine flow (member B ratifies and shares; member A has a local
    commit and Syncs) that range contains B's branch *content commit*, which carries the same
    `Org-Proposal` trailer but is not itself "ratified in this very commit", and it skips B's ratify
    merge. A legitimate history was reported (proof G shows both ranges). The trunk line of the
    incoming side contains only the commits that were trunk commits on their own machine: events, a
    Propose, a ratify merge. Those are exactly the commits the table judges.
  - **Each commit is judged against its own parent.** The walk does not carry one running state down a
    line: for every commit it reads `governance.yaml`, `members.yaml` and `proposals.yaml` at that
    commit's first parent (`git show <parent>:<file>`, cached by blob id). The roles and rules in
    force for a commit brought in by a Sync are those of the machine it was made on.
  - **A merge that is not what git itself would make of its parents is a finding (M-e).** The second
    draft took the paths where `M` differs from *both* parents. That catches an added file (`evil.txt`)
    and misses a merge that silently *drops* one side's change, because the file then equals one parent
    (proof ME.3: a Sync merge that kept the local ledger and the local `incoming.txt` is reported by
    neither parent comparison). The check is now against git's own answer: for a merge with no
    `Org-Proposal`, `git merge-tree --write-tree P1 P2` gives the tree git would build (its first line is
    that tree's id, also when it exits 1 on a conflict; the same git 2.38 floor Sync already has, §3.12).
    The paths where `M`'s tree differs from that tree (`git diff-tree -r --name-only <that tree> <M tree>`)
    are looked at in two groups, split by the list of files git could not merge (`git merge-tree --write-tree
    --name-only P1 P2` prints them after the tree id, up to the first blank line; proof HR):
    - **A path git merged cleanly** that differs is a finding. Nobody has a reason to touch it by hand, and this is
      where a silent drop or an extra file shows.
    - **A path git reported as conflicted** is one a person resolved, which §3.12 tells them to do; the merge then
      holds text git could not have built, so its content is not compared (comparing it made the remedy the
      validator's own message asked for a finding that nothing could clear: M-1 of the third review). It is
      reported as a *warning*, "resolved by hand: `<path>`, review it", naming the commit, at every severity,
      `--strict` and `CI=true` included (every conflicted path warns, whether or not it differs from `merge-tree`'s tree: amended at build, P2-B47). The one path the validator can check is `data/proposals.yaml`: its content
      must equal `mergeLedgers` of the merge base's copy and the two parents' copies (the same pure function Sync
      used), or it is a finding. A trailer-less merge's ledger is compared with `mergeLedgers` **by id**, the entries as sets and not positionally, because Sync writes ours' order with the incoming entries appended (amended at build, P2-B30); the check runs whenever the ledger conflicted. A clean Sync merge differs from `merge-tree` in
    no path (proof ME.1); an extra file is reported (ME.2); both dropped paths are reported (ME.3); a
    ledger merged by id differs only in `ledger.yaml` (the instance's `data/proposals.yaml`, ME.4). On a
    git older than 2.38 the validator cannot ask, and says "merge expansion needs git 2.38; this merge
    was not checked" as a warning (an error under `--strict`/`CI=true`), never silently passes. This stops
    a merge being used to carry an unreviewed change into, or to remove a reviewed change from, **any path git
    merged cleanly** (and `data/proposals.yaml`, which it checks by content); it does not stop it inside a file
    git could not merge.
    **The limit, said plainly (M-C of the fourth review):** inside a file git reported as conflicted nothing is
    compared, so a hand resolution can **add** a change as well as drop one: a laxer rule in a conflicted
    `data/governance.yaml`, a role in a conflicted `data/members.yaml`, or a lost reviewed change. The validator
    names the file and the commit as a warning and a person reads it; **for a path in a class whose rule is not
    `direct` for the person who resolved it, that warning is the only signal there is, and it cannot fail CI**
    (§6). Two members changing the same governed file at once is where it matters. The remote's refusal of a
    non-fast-forward push (§3.12) is not a lock against it: that refusal is what sends the later person into the
    Sync that conflicts. A narrower check, kept open for a later round and not built in P2, would make a finding
    of a hand resolution in classes `governance` and `identity` unless the resolved file equals one of the two
    parents. Proof HR (git 2.43): two changes to `reg.yaml`, resolved by hand
    (`UU reg.yaml`, then a commit): `merge-tree --name-only` lists `reg.yaml` as conflicted, and the merge differs
    from `merge-tree`'s tree in `reg.yaml` only, a finding under the old rule and a warning under this one
    (HR.A); the same merge that also deletes the cleanly merged `in.txt` differs in `in.txt` as well, still a
    finding for that file (HR.B); an honest merge with no conflict lists no conflicted file and differs in no path
    (HR.C). `merge-tree --write-tree` writes the tree it computes into the repository's object store
    (`git cat-file -t` on its id answers `tree` afterwards); it moves no ref and touches no working file. The
    validator is read-only for refs and files, not for the object store, and git's garbage collection removes
    the unreferenced trees.
  This amends F2-R6 ("a merge is one change against its first parent") for merges that carry no
  `Org-Proposal`; with the trailer the merge stays one change.
- **The M-3 sentence (amended at build, P2-B33).** For a hand edit of a rule that no proposal can carry, the validator does not say "revert the commit". It says that no proposal can carry a change of class <class> (<file>) until P2b, that the finding stays while the commit is among the last `--max` commits, and that to clear CI the CI command's `--range` should start after it (§6 names that way out). The sentence names the class or file, not the identity of the person.
- **Only where rules are written (M3).** The ledger check, the decision-row rule, the clock rule and
  the merge expansion run for a commit **only when the rules in force at its parent are written** (for a trailer-less merge, when any parent has written rules: P2-B46), the
  same test F2 uses to judge a history at all: `read.governance !== null && !implied && rules.length >
  0` (`scripts/validate-governance.mjs`). A solo or rule-less history (the solo default, or a
  `governance.yaml` with `decisions: []` and no `rules`) is not walked by any of this, merges
  included, and `proposals.yaml` need not exist. A solo maintainer who hand-adds a `decisions[]` row
  to such a file gets no finding. The first commit that *writes* rules is judged by nothing new (its
  parent has none), as in F2. Two tests pin it (Task 14a-1, 14b): a solo maintainer's
  history (solo, `decisions: []`, hundreds of commits, thirty merges, no `Org-` trailers, no ledger) is
  clean under `--strict`, with and without a hand-added row; and the same instance after rules are
  written starts being judged from that commit on.
- Severity stays F2-R7's: a warning locally, an error under `--strict` or `CI=true`.
- The note that a trailer is only a visibility measure is replaced by a truer one: **the ledger is
  checked for form, rule, standing and (for a ratify) content, not for signature.** It closes F2's
  trailer hole for *existence* and *content*; it cannot close *authorship* or *time* (next bullet). Git authorship is the actor's claim until
  sign-in (P5); an attacker with write access can still write a commit as someone else. §6 says so.
- **Time (M5, P2-R30).** Every window check evaluates "at the commit's date", and the date is the
  committer date the machine wrote: as forgeable as the author. The validator therefore does the
  bounded things it can: an event's `at` and a proposal's `opened` must lie within `CLOCK_SKEW` of the
  commit that adds them (a stale `opened` on a new proposal is a finding); the ratify merge's date
  is git's own, within `CLOCK_SKEW` of the evaluation's now and at or after its whole-second floor (amended at build, P2-B18), so a ratify dated before a window closes fails the `met` check; and
  the server refuses to write when its own clock is behind the ledger (§3.2). It does not claim to
  detect a deliberately false date (§6).

### 3.11 Systems: the outside outcome, read-only

A rule `decide: { by: system, system: <id> }` is decided by an outside system, never by the platform.

- **Prepare, then attach (M6).** The proposal commits to *one specific transaction*, not to "some
  executed transaction". For a Safe, the driver's `prepare` step (P1 reserved it; P2 implements it for
  class `treasury`) takes the proposal and yields the payload (`to`, `value`, `data`, `operation`)
  and the **Safe transaction hash** computed from it, with a link to open it in the Safe app.
  **How the hash is computed (M-d).** It is the Safe's own `getTransactionHash`: Keccak-256 of
  `0x19 0x01`, the domain separator (Keccak-256 of the ABI encoding of `DOMAIN_SEPARATOR_TYPEHASH`, the
  chain id and the Safe's address) and the struct hash (Keccak-256 of the encoding of `SAFE_TX_TYPEHASH`,
  `to`, `value`, Keccak-256 of `data`, `operation`, `safeTxGas`, `baseGas`, `gasPrice`, `gasToken`,
  `refundReceiver` and the Safe's `nonce`; the five gas and refund fields are zero in the payload `prepare` yields). **Keccak-256 is not in `node:crypto`** (`createHash('keccak256')` throws
  "Digest method not supported"; `sha3-256` is NIST's function with different padding and gives a different
  digest, proof K), and the package may add no dependency (role rule). **Decision: the repository holds its
  own Keccak-256**, `lib/keccak.mjs`, pure, about forty lines (the prototype in proof K is 36), built first
  and alone (Task 12a). It is held to published values, not to itself: the empty string and `"abc"` from the
  Keccak team's vectors, the selector of `transfer(address,uint256)`, **and the two constants of the Safe
  contract** (`DOMAIN_SEPARATOR_TYPEHASH`, `SAFE_TX_TYPEHASH`) that the code recomputes from their type
  strings and that matched in proof K; the test also asserts the NIST padding gives a different digest, so
  it can fail, and includes one vector longer than the 136-byte block taken from a published list (the
  engineer cites the source; the task stops if none is found). The Safe's transaction hash itself is
  checked against one published transaction-hash example from the Safe's documentation or test suite, cited
  the same way. The chain id and address come from the `systems.yaml` record; the nonce and the contract
  version from the same `api.safe.global` host the driver already declares (`/v1/safes/<address>/`); a
  Safe older than 1.3.0, whose domain has no chain id, is answered in words and gets no hash. The
  alternatives, if you prefer one (§5 question 12): add a Keccak dependency (operator's word), or store
  `{to, value, data_hash, operation, nonce}` in `attach` and let `outcome` match those fields without a
  hash (weaker: any transaction with the same fields would match). Submitting it is an external
  write that only a signer does in the Safe app: the platform prepares, frames and reads
  (architecture §6). A member who may propose then records the reference with an `attach` event:
  `ref: { system: treasury-safe, id: "0x…", payload: { to, value, data_hash, operation, nonce } }` (`operation` and `nonce` are hash inputs, so attach verifies the hash without a network read and a moved nonce is detectable: amended at build, P2-B25). The server refuses an
  `attach` whose `id` is not the hash `prepare` gives for that payload, and **refuses a hash already
  attached to another proposal** (it scans the ledger). A proposal has at most one live `attach`; a
  second one replaces the first only while no `system` event exists for the current `rev`'s attach. **The lock is per `rev`** (attach and `system` events record `rev`; a revision asks for a new attach), and a reading of a transaction the service does not know yet (404) is never appended, so it locks nothing (amended at build, P2-B26).
- **Read.** The Safe driver's `outcome(ref)` reads
  `GET /v1/multisig-transactions/<safeTxHash>/` on `api.safe.global` (a host the driver already
  declares) and answers `pending | executed | failed` with the confirmations against the
  threshold, **only after checking that the transaction it read is the one the proposal committed
  to**: the response's `safeTxHash` equals `ref.id`; its `to`, `value` and the hash of its `data`
  equal `ref.payload`; **the hash computed again from every field of the response equals `ref.id`** (the service's own `safeTxHash` field is not trusted: amended at build, P2-B27); and its `submissionDate` is **after the proposal's `opened`**. A mismatch is
  not `executed`: it is a reading `mismatch` with the sentence "this transaction is not the one the
  proposal prepared", which the evaluator treats as `pending`. It follows the driver contract: cached, timed out at 8 s, a failure is attention and
  never a thrown error.
  **Two limits, stated (LOW-6).** A Safe transaction prepared in the Safe app *before* the proposal was
  opened is refused (`submissionDate` before `opened`), and the Safe's `nonce` is part of the hash and can
  change before execution (another transaction executes first); either makes the proposal unmatchable. The
  author withdraws it and proposes again, or revises it (a `revise` re-prepares with the current nonce and
  a new `attach`). That is the price of committing to one transaction, and the page says so in words when
  a reading is a `mismatch`.
- **Final readings (amended at build, P2-B27).** An `executed` or `failed` reading is final for its attach: a later reading is not appended.
- **Prepare is a route (P2-B24).** `POST /api/proposals/:id/prepare` (§3.15) takes the transaction the author typed on the page and returns the payload, the Safe transaction hash, the Safe app link and the `ref` to attach; it reads the nonce and posts nothing. No proposal of class `treasury` can be opened in P2: a proposal's classes come from its ops, Propose refuses a change with no ops (`EMPTY`), and the engine stages no treasury record (P2-B33). The Safe driver refuses `prepare` unless the proposal's classes include `treasury`, so prepare, attach and check are built and tested but have nothing to serve on real data until a treasury record can be staged (corrected at write-up).
- **Record.** When the reading differs from the latest `system` event, the server appends one
  (`by: system:treasury-safe`, `outcome`, `ref`) as a commit like any event. The evaluator reads
  *that event*, not the network, so `evaluate` stays pure and the ledger keeps what was read and when.
  A read that fails records nothing and raises attention on the proposal.
- **Who triggers a read.** Opening the proposal page (`GET /api/proposals/:id` is the trigger: for a member, when the proposal is open and has a live attach on its current `rev`, it reads at most once per the reader's window and records a changed reading, P2-B24), and *Check now*. There is no background poll
  that writes; a person looking triggers the commit (P2-R3 again).
- **Only the server writes `system` events.** The validator allows `by: system:*` events and cannot
  prove who typed them (§6); it checks that the system exists and that the proposal has a matching
  `attach`.

### 3.12 Reaching each other, before hosting (architecture §6)

There is no sign-in until P5, so several members work as separate checkouts of one repository, each
running the platform on their machine, with a shared remote. P2 does **not** make a network
service. It gives those checkouts three plain, explicit things:

- **The ledger is the shared state.** Everything a member needs to see or decide a proposal is in
  `data/proposals.yaml` on the trunk (ops, events, rules). The branch is rebuilt locally, so no
  branch needs to travel.
- **Fetch is the one network read, and it goes through the executor (L1).** `git fetch` uses the
  member's own credentials against a remote, so it is a catalogue **operation** with `network: true`
  (`needsConfirm` is true): plan ("fetch `origin`: it downloads, it changes no file"), nonce, a
  person's confirmation, job. It writes only the remote-tracking refs. *Sync* below starts with it.
  **Propose, Ratify and the closings never fetch on their own.** They read the *last* fetch and refuse in words if it is older than `PT15M` or
  shows commits the trunk lacks: "Sync first: the remote has 2 commits you have not merged." **The
  reader is its own small function, `lastFetch(repo, trunk)`, built in Task 5a with the rest of the git
  module (M-c), before any task that tests "Sync first".** It does no network. **Age and subject both come from `FETCH_HEAD`** (the file `git rev-parse --git-path
  FETCH_HEAD` names; a file read, no git command beyond that path lookup): the reading is fresh only when the
  file is younger than `PT15M` *and* names the trunk, meaning one of its lines has a third tab-separated field
  beginning `branch '<trunk>' of ` (also when the line is marked `not-for-merge`, as a plain `git fetch` of a clone
  sitting on another branch writes it) *and* that line's sha equals `refs/remotes/<remote>/<trunk>`. Any
  `git fetch` rewrites `FETCH_HEAD` with only the refs it fetched, so an unrelated `git fetch origin
  other-branch` leaves a fresh file that does not name the trunk, and reads as "the last fetch was not of the
  trunk: Sync first" (proof FH: after that fetch the file held one line, for the other branch, while the tracking
  ref sat behind the remote and `behind` read 0). A fetch that finds nothing new rewrites the file and still names
  the trunk, a `--dry-run` leaves the file alone, a trunk named `release/1.0` reads from `branch 'release/1.0' of`,
  and a fresh clone has none, so a missing file reads as "never fetched" (proof LF). (Amended at build, final review I2: a member's own Share moves the tracking ref to what it pushed and leaves `FETCH_HEAD` naming the tip it fetched, so the reading is also fresh when that line's sha is an ancestor of the tracking ref and the tracking ref is an ancestor of, or equal to, the local trunk: the only difference is what this clone pushed. A teammate's push, once fetched, still reads as behind.) A hand-run `git fetch origin
  <trunk>` is a fetch of the trunk and counts, which is what the person doing it means. The remote's refusal of a
  non-fast-forward push remains the lock that holds (below). "Behind" is
  `git rev-list --count <trunk>..refs/remotes/<remote>/<trunk>` (a read;
  "ahead" is the same with the arguments swapped). Task 13a then builds only the `fetch` operation and
  Sync.
- **Sync** (a button, never automatic): the *fetch* operation above, then the local part, which the
  server does under the write lock:
  - the trunk is behind and the tree is clean: `git merge --ff-only`;
  - the trunk diverged: `git merge-tree --write-tree` first to find conflicts without touching the tree. If
    the only conflicted file is `data/proposals.yaml`, the platform merges the ledger by id (below) and
    commits the merge; any other conflict is **refused in words** ("both sides changed
    `data/governance.yaml`; resolve it with git, then Sync again") and nothing is touched. The merge the person then makes is read by
    the validator as "resolved by hand: `data/governance.yaml`, review it", a warning at every severity (§3.10, proof HR).
    `merge-tree --write-tree` needs **git 2.38 or later** (L5): the first step of Sync reads `git
    --version`, and on an older git Sync still fast-forwards but refuses to merge a divergence ("this
    machine's git is 2.34; Sync needs 2.38 to merge two histories safely; update git, or merge with
    git yourself").
  - the ledger merge (`mergeLedgers(base, ours, theirs)`, pure, in `lib/proposals.mjs`) is by id:
    entries are unioned; an entry's events are unioned by id and ordered; for a field both sides
    changed, the final state wins (`ratified` over `open`), the side with the later `revise` event
    wins `ops` and `rev`; anything else it cannot decide is refused naming the entry. The merge commit
    carries no `Org-Proposal` and the validator expands it by the first-parent rule of §3.10.
- **Share** (a button, confirmed): `git push` of the trunk, as a catalogue **operation** through the
  executor (plan → nonce → job), so the person sees exactly what will be pushed (`origin <trunk>`),
  and the executor's own check applies. Its declaration is `writes: []` and a push moves no local
  file or HEAD. It never forces and never pushes anything but the trunk (P2-R18). `proposal/*`
  branches are not pushed. **How "never forces" is made true (M1):**
  - *The trunk name is validated before it is used anywhere* (`validTrunkName`, one function, in
    `lib/rules.mjs`, used by `checkGovernance` for `governance.trunk`, by the server for the branch
    checked out at start, and by the `share` operation's plan builder): it must match
    `^[A-Za-z0-9][A-Za-z0-9._/-]*$`, hold no `..` or `//`, not end in `/`, `.` or `.lock`, not begin
    with `refs/`, and not be `HEAD`, `MERGE_HEAD`, `ORIG_HEAD` or `FETCH_HEAD` (LOW-2: a branch of
    one of those names makes `git rev-parse --verify MERGE_HEAD` answer "present" with no merge in
    progress, proof L2; the platform therefore tests for a merge by the file `git rev-parse --git-path
    MERGE_HEAD` names, §3.8). The pure function cannot ask git, which rejects names the pattern accepts
    (`a/.b`, `a.lock/b`; proof L1), so the **server** also runs `git check-ref-format --branch <name>` on
    the trunk at start and before each `share` plan and refuses a name it rejects: a second guard, never
    the only one. A name beginning with `+`, `-` or `:`, or holding `:` `*` `?` `[`
    `\` `@{` or a space, is refused with the sentence "`+main` cannot be the trunk: git would read
    it as an instruction to overwrite `main`". `git check-ref-format --branch '+main'` exits 0, so
    git alone does not protect us (proof P).
  - *The refspec is built by the platform in full*: `git push -- origin
    refs/heads/<trunk>:refs/heads/<trunk>`. The leading `refs/heads/` makes any later character a
    branch-name character, never a force marker; a refspec configured in `remote.origin.push` is not
    consulted when the command line names one (proof P). The plan prints that exact line.
  - *The executor's `RULED_OUT` list is an exact-token match* (`'-f'`, `'--force'`, …) and does not
    see `+main` or `refs/heads/+main`; the `share` operation therefore does not take a free-text
    argument at all. Its argv is assembled from the validated trunk and the remote name only, and a
    test gives it a trunk named `+main` (refused), `main:other` (refused) and `release/1.0` (accepted,
    with the exact refspec).
  - *A push that git itself rejects as not a fast-forward is reported, never retried with anything
    else* (proof P: the rejection is plain, exit 1). (Amended at build, final review I3: the page follows the Share job to its end and says "The remote
    has commits this clone lacks: Sync, then Share again." on a rejection. Final review M8: when that Sync then refuses,
    after a double ratify race or an id collision of the shape before the random suffix, the recovery is by hand,
    outside the platform: a fresh clone of the remote, and the unshared work done again there; the steps are in the
    admin README, "When Sync cannot merge".)
- **Optimistic concurrency for decisions.** *Propose*, *Ratify* and the closings require the trunk
  to be up to date with its remote *as of the last fetch* (above). Events do not: the ledger merge
  makes concurrent events safe. A repository with no remote skips the check. This **narrows** the
  window in which two ratifications collide in `governance.yaml` and `DECISIONS.md`, which Sync will
  not merge; it cannot close it, because someone can push a moment after the fetch. The lock that
  does close it is the remote's own refusal of a non-fast-forward push: the second ratifier's Share
  fails, their Sync then refuses on the conflict in words, and the validator would have caught a
  second ratification of a closed proposal ("a closed proposal changes", §3.10).

What the member sees: a small status in the Governance head ("2 commits not shared · 1 new from the
remote"), *Sync* and *Share* buttons, and a sentence when Sync refuses.

### 3.15 Server routes

Opening, deciding and merging are server operations on the live plane (architecture §4.4). All
inside the repository's write lock; all through `transition()` for the proposal machine, so a refusal
is `409 { code: 'REFUSED', machine: 'proposal', state, event, reason }` (amended at build, P2-B12: the one code of the platform's `MachineRefusal`, P4-R2).

```
GET  /api/proposals                    → ProposalView[]     the list, with the derived state, evaluation, needsYou
GET  /api/proposals/:id                → ProposalView & { diff, note?, current }   (ops and events are the entry's own fields; for a member this is also the page-visit system read, §3.11)
POST /api/proposals                    { title, rationale, statement? } → 201 ProposalView | 403 | 409 | 422
POST /api/proposals/:id/events         { kind, text?, vote?, of?, ref? } → ProposalView
POST /api/proposals/:id/load           → ChangeView          (Revise: stage the ops into the author's tray, marked `revises`)
POST /api/proposals/:id/revise         { ops } → ProposalView   (the tray's Update proposal)
POST /api/proposals/:id/prepare        { to, value, data, operation } → { payload, safeTxHash, appLink, ref }   (reads the nonce; writes nothing)
GET  /api/generated                    → { behind: boolean, since?: <commit> }   (§3.8; local history only)
POST /api/proposals/:id/replay         { choose? } → ProposalView   (409 naming the stale ops it cannot re-base)
POST /api/proposals/:id/ratify         → ProposalView & { commit, decision }
POST /api/proposals/:id/close          { outcome: 'rejected' | 'expired' | 'withdrawn' } → ProposalView & { commit, decision }
POST /api/proposals/:id/check          → ProposalView        (a system read; may append a `system` event)
POST /api/sync                         → { state: 'up-to-date' | 'fast-forwarded' | 'merged' | 'refused', … }
GET  /api/sync                         → { ahead, behind, remote } (reads the last fetch; no network)
```

- `ProposalView` is the ledger entry plus `{ derived: 'stale'|'objecting'|'voting'|'approving'|<final>,
  evaluation: Evaluation, rules: RuleSummary[], stale: number[], needsYou: boolean, can: EVENT[], cannot: Record<EVENT, string>, check: true | string, branchState: 'built'|'missing', attention? }`.
  `can` is `enabled(proposal, guards, state, context)` for the current actor, so the client never
  decides what is allowed (P4 §3.2); `cannot` is each event the actor may not write now, with the machine's sentence (empty for a non-member). The build state is `branchState`, because `branch` is the ledger's name for `proposal/<id>` (amended at build, P2-B11). `GET /api/proposals/:id` adds `diff`, `note?` and `current` (each op's record as the trunk holds it now).
- **Every proposal route answers a `ProposalView`** (amended at build, P2-B51): propose (201), events, check, revise, replay, close and ratify answer the view as the actor sees it after the write, with what the write said beside it (`commit`, `decision`, `note`, and for check `reading`, `appended`, `attention`). `load` answers the tray's `ChangeView`, marked `revises`.
- **Remote (P2-B29).** The remote is `origin` only in P2, for Sync and Share.
- **Sync and Share are the instance's own operations** (amended at build, P2-B65): the instance's own card exists whether or not a fleet is declared, so both are reachable on a solo clone. Every git process the server starts runs with `GIT_OPTIONAL_LOCKS=0`, set once by the git module on load, so a read never takes git's index lock (P2-B67, P2-B68).
- `effectiveRule` is replaced, not wrapped: it returns the same `RuleSummary` shape, now with
  `proposable: true` and no "Proposals arrive with P2" clause; `Apply` still requires `direct`.
- **The git module's whole vocabulary (M2, L2).** Today `server/git.ts` runs: `status`, `ls-files`,
  `config` (read), `rev-parse`, `log`, `add`, `commit`. P2 adds, and only adds, the rows below. This is
  the complete list; a command not in it is not run.

  `push` is **not** in this module: it exists only as the `share` operation through the executor. There

  **`commitMerge` and the guardrail (L2).** The module's `assertInsideData` refuses to commit a path
  outside `data/`, and it stays exactly as it is for every existing caller. `commitMerge` is a
  separate function that takes **no paths**: it commits what is already staged, after checking
  `git diff --cached --name-only --no-renames` against the `allowedPaths` its caller passes (the files the ops
  name, `data/proposals.yaml`, `data/governance.yaml`, `DECISIONS.md`), and refuses on any other
  name. `DECISIONS.md` is therefore allowed only by `commitMerge`, only when ratify asks for it.

  **How the vocabulary is held (M2, M-a): an allowlist, not a blacklist.** The first version of this
  test scanned string literals for forbidden words. The re-review showed it cannot see a *method call*
  on the client (`.clean('f')`, `.stash()`, `.push(...)` carry no literal), a concatenated name
  (`'res' + 'et'`), or a command it did not think to list (`checkout -- .`, `rebase`, `branch -d`): all
  pass a blacklist of literals. The guard is inverted; a command is forbidden unless it is on a list.
  The test parses `git.ts` with the TypeScript compiler API **and its type checker**, and fails on any of:

  1. **Imports.** A module specifier outside the fixed list (`node:path`, `simple-git`,
     `../lib/trailers.mjs`, and the modules Task 5a itself names in the test); in particular
     `node:child_process` and `child_process`; any `import(...)` or `require(...)` call.
  2. **Subcommands and their flags (M-2 of the third review).** The first element of the array given to
     `raw(...)`, and the first argument of the private `run(...)`, must be a **plain string literal that is a
     key of `ALLOWED`**. A concatenation, a template with a substitution, a variable, a spread or an empty call
     is a failure ("not a plain literal"); so is a first element that begins with `-` (`-c core.hooksPath=…`
     and `-C <dir>` are global options git reads before the subcommand). **`ALLOWED` is a map from subcommand
     to the exact flags it may carry, not a list of subcommands plus a list of forbidden words**: every other
     element of the array that begins with `-` or `+` must be in that subcommand's list, compared as the whole
     token (`--output=data/x` is not `--name-only`), and nothing after a bare `--` is a flag. The second
     version checked later literals against a blacklist (`--force*`, `-f`, `-D`, `--hard`, `--mirror`,
     `--delete`, `--no-verify`, a leading `+`) and so passed `update-ref -d`, `diff --output=…`, `commit -n`,
     `worktree prune` and `merge --strategy-option`, each a command that is on the list with a flag nobody
     had listed (proof GA); a flag that is not listed is now refused whatever it does. The map, which is the
     table above read column by column:

     ```
     ls-files: -v --error-unmatch · log: -1 --format=%B · rev-parse: --git-path --verify -q
     diff: --name-only --cached · diff-tree: -r --name-only · merge-base: --is-ancestor
     rev-list: --first-parent --reverse --count · worktree: verbs add|remove, flag --detach
     update-ref: no flags; exactly refs/heads/proposal/<id>, a 40-hex new value that is not all zeros, a 40-hex old value (all zeros allowed here only, meaning "create")
     merge: --no-ff --no-commit --ff-only --abort · merge-tree: --write-tree --name-only
     fetch: none · show: none · check-ref-format: --branch · commit: -F · (and --version alone)
     ```

     **The same check runs at `run`'s choke point on the real argv, before a process starts**, so a flag held
     in a variable, which the static scan cannot read, is still refused; the scan and the runtime check read
     one `ALLOWED`. Proof FS ran the map as a function on a scratch table (27 argv accepted, 33 refused). That table
     was not kept, so no count is a requirement (LOW-5 of the fourth review): Task 5a **derives** its table from
     `ALLOWED` and the plants below, by the recipe in the plan, and the test asserts every row.
  3. **Client methods.** For every property access on a value whose *type* is simple-git's `SimpleGit`
     (found by the type checker, so `const g = simpleGit(r); g.clean()` is seen as well as
     `simpleGit(r).clean()`), the method name must be in a fixed list, `add commit status revparse
     getConfig raw` (and the module's own `run`). Element access on such a value (`g['clean']`) and
     destructuring it (`const { clean } = g`) are failures. **The arguments of the allowed methods are read
     too (M-2c):** `.add(x)` takes one argument; `.commit(message, paths)` takes exactly two, the second an
     array expression or an **identifier whose type, read by the checker, is `string[]`** (LOW-4 of the fourth
     review: an identifier holding an object or an array of flags would pass on its form alone), never an object
     literal and never a third argument; `.status()` takes
     none or `['--', ...paths]`; `.getConfig(key)` takes one literal; `.revparse([...])` and `.raw([...])` are
     held to the map of rule 2. `simple-git` appends an options object or array to the command line
     (proof GA: `commit('m', paths, {'--no-verify': null})` ran `commit -m m a.txt --no-verify`, and
     `add(['-f', path])` ran `add -f ign.txt`), which is why the third argument is refused. At run time the
     paths a write receives also pass `assertInsideData`, which refuses a path such as `-f` (it resolves to
     `<repo>/-f`, outside `data/`).
  4. **The client's options.** `simpleGit(repo, { … })` may carry the key `errors` only (not `binary`, not

  5. **Blinding.** The `any` keyword, and the comments `@ts-ignore`, `@ts-expect-error`, `@ts-nocheck`,

## 4. Testing

- **`lib/evaluate.mjs`**: vitest, no I/O. A table per method: approve (count, author excluded,

  (before/at/after the window boundary, objection holds, revision restarts, an objection from a
  non-decider is a comment), vote (quorum by abstention, threshold exactly at the boundary, quorum

  (each reading, an unrelated executed transaction, a mismatched `to`/`data`, a transaction submitted before `opened`: all stay `pending`), `direct` as approve, TTL and `expires`, **the pinned cases of §3.6 one by one (M7)**: an all-abstain vote, a vote at and after `closedAt`, met-and-expired, an unmeetable `approve` and its `checkGovernance` warning, abstention against `threshold`, several rules (all met, one failed, one

## 5. Questions for the operator

Marked **★** are the ones to see first: they decide who holds power in the loop, or loosen a rule the
safety rules set.

1. **★ Four eyes (P2-R2).** An author's own approval does not count under `approve`. A maintainer who
   proposes needs another. Right for a coop; wrong for a three-person group where the author is the
   only one with the expertise, and a deadlock for a rule whose `count` equals the number of deciders
   when the author is one of them (the evaluator says "cannot be met" and `checkGovernance` warns,
   §3.6). The alternative is the rule key `self_approve: true`, which the build ships either way (Task 2 adds
   it to the rule vocabulary, the schema, the evaluator and the machine's guard, default false), so your
   answer is one default, not a change of code.
2. **★ Several rules, every one must be met (P2-R1).** One proposal, decided when all the rules for
   the classes it touches are met, rather than one proposal per rule.
3. **★ Ratify is always a person (P2-R3).** When the consent window closes, nothing happens until a
   person presses *Ratify*. An alternative lets the server merge by itself when a rule is met.
   That would be a decision made by software (charter principle 12).
4. **★ Git, beyond what the platform may do today (P2-R15).** `server/git.ts` says the platform
   never does reset, clean, stash or force. P2 adds the list in §3.15 (worktree, update-ref on
   `proposal/*` only, merge, merge-tree, fetch, diff, rev-list), and **one undo, `merge --abort`**,
   with a test that reads the code's string literals and fails on the forbidden words. `merge --abort`
   is the one command that could be mistaken for a reset; it runs only after ratify required a clean
   tree, has computed and validated every new text, and staged each file it wrote (§3.8). If you would
   rather the platform had **no undo at all**, §3.8 describes the plumbing alternative (build the merge
   commit off to the side, then move the trunk by fast-forward): nothing to abort, a longer vocabulary.
   Say which.
5. **★ Sharing (P2-R18, amended).** Sync fetches (through the executor, with a confirmation, because
   it reaches the network with your credentials) and merges; Share pushes the trunk, never forced, with
   a refspec the platform builds in full and a trunk name it validates, through the executor with a
   confirmation. Propose and Ratify read the last fetch and ask you to Sync when it is old. The
   alternative is to leave all pushing to people and only report "2 commits not shared".
6. **★ `.well-known/` after a ratify (P2-R20).** `.well-known/**` is class `identity`, so a regeneration
   after a ratified `records` change would need its own decision. Proposed: the regeneration is an
   `operations` change, and F2's `governedClassOf` treats a commit that carries `Org-Rule: operations/…` and
   touches only `.well-known/**` as `operations`, not `identity`. Not built in P2; it needs your word.
7. **★ Crew branches (P2-R21).** Architecture §4.7 says merging an agent's branch is itself a
   proposal. P2 builds proposals from staged operations only; a proposal whose content is a branch
   is not here. The solo instance is unaffected (it is `direct`). A consensus instance with a crew
   would want it next.
8. **★ The ledger is judged, not exempt (P2-R13).** The answer to F2's question (are proposal-event
   commits exempt?): they are judged by the ledger check, not by class, so the exemption is no hole.
9. **`P30D` default expiry (P2-R11)**, a rule key `expires`, and the vote and consent windows starting
   at the last revision.
10. **`Org-Rule: <rule id>/<method>` (P2-R14).** A solo instance's commits will read `solo/direct`
    where they read `records/direct`. The class leaves the trailer, so P3's activity trail infers it.
11. **★ Where the content of a proposal lives (P2-R6), added by the review.** The architecture says the
    change lives on a `proposal/<id>` branch. P2 puts the operations in the public ledger
    `data/proposals.yaml` and makes the branch a local cache. That is a better fit for members on
    separate machines, and it changes where the truth is: a public repository holds a proposal's
    content before anyone has decided it. If you prefer pushed branches, R6 and R18 change together.
12. **★ A Keccak-256 written in the repository (P2-R32), added by the second review.** A Safe
    transaction's hash (§3.11) is an EIP-712 digest, and Keccak-256 is not in `node:crypto` (it answers
    "Digest method not supported"; its `sha3-256` is a different function). The rules forbid a new
    dependency without you. Proposed: about forty lines in the repository, checked against the published
    vectors and against two constants of the Safe contract that the code can recompute (proof K). Say if
    you would rather add a dependency, or drop the hash and have `attach` store the transaction's fields
    (§3.11).
13. **★ Can a rule be changed by proposal in P2? (P2-R33), found by the second fix round and corrected by the
    third.** Not as the engine stands (§6): an op cannot name `governance.yaml`. The earlier draft said rule changes
    "stay by hand". That is not a fallback on a consensus instance: a hand edit of a rule is judged by the rule in
    force before it, and a rule that is not `direct` for the author needs a ratified proposal that no op can carry,
    so the commit is a finding, and the validator's own sentence ("Propose the change, or ask a maintainer to
    revert it") offers a proposal that cannot be made (proof RH). Until the engine stages document edits (`P2b`),
    a consensus instance **cannot change a rule validly at all**. Your choice: (A) put `P2b` inside P2: Task 11a grows
    by the engine change (a document-edit op for `governance.yaml`) and one task is added before it; (B) leave it for
    `P2b` after P2 and accept that a consensus instance, once its rules are written, cannot amend them by the process
    it runs. **What B costs (M-A of the fourth review):** a maintainer who must change a rule meanwhile commits it
    by hand, and `validate:governance` reports that commit as a finding. The script has no acknowledgement, baseline
    or exemption (its options are `--strict`, `--max <n>` and `--range`, read in `scripts/validate-governance.mjs`);
    the finding is a warning locally and an **error under `--strict` or `CI=true`**; and the commit stays inside the
    walked window (the newest 500 commits by default) until 500 later commits push it out. So an instance whose CI
    runs the check is **red on every run for as long as that commit is in the window**, not one footnote. The ways
    out are a `--range` in the CI command that starts after the commit (the history before it is then no longer
    judged there), or choosing A. Writing the first rules, a solo or rule-less instance, and any rule the author
    may apply alone are unaffected either way. Recommended: B, with this cost in view. Document edits are their own piece of P1's engine (edits inside a commented YAML
    document), and what P2 delivers, deciding records, does not wait for them.

## 6. What P2 does not do

- **No sign-in.** The actor is the local git identity (architecture §6). `by` is the claim of the
  machine that wrote it; the ledger check verifies form, rule and standing, not a signature. The
  shared remote's write access is the only lock until P5.
- **No proposals from a branch** (question 7), no proposal from outside a change (an agent's raw
  commit), no co-authored proposals.
- **No early close of consent** when every decider has agreed (a later refinement).
- **No defence against a false date or a false author.** The validator bounds honest clock skew and
  checks form, rule, standing and content; a person with write access who writes `GIT_COMMITTER_DATE`
  or another person's email can still do it until sign-in (P5).
- **No automatic ratification, no background writes.** The clock changes what the screen says, never
  the repository.
- **No execution on chain.** The Safe is read and prepared for; a signer submits (architecture §6).
  Snapshot, Gardens and Hats outcomes wait for F3's modules; `system` rules for them read as
  "no driver reads this system yet".
- **No `generate:schemas` inside a ratify** (§3.8).
- **No merge of `governance.yaml` or `DECISIONS.md` across machines** (§3.12): Sync refuses and
  says why.
- **No push of proposal branches**, no deletion of any branch, no pruning.
- **Splits stay inert** (F2-R21): `classes` are whole classes.
- **No UI to author rules, and rules are not proposable through the tray yet.** The architecture says
  rules are changed by proposing a change to `governance.yaml` (class `governance`), decided under the
  rule in force before it. P1's change engine stages only collection registries, so an op cannot name
  `governance.yaml` (a document registry), and the `governance` and `identity` classes, for which the
  Propose form demands a `statement`, are not reachable by ops either. Until the engine stages document
  edits, **a consensus instance has no valid way to change a rule**: a hand edit of `governance.yaml` is judged by
  the rule in force before it, as F2 built it, and a rule that is not `direct` for the author needs a ratified
  proposal that no op can carry, so the hand commit is a finding (a warning locally, an error under `--strict` or
  `CI=true`; proof RH). **The finding cannot be acknowledged**: the validator has no baseline or exemption, and the
  commit stays in the default 500-commit window, so a CI that runs it is red until 500 later commits push it out
  or the CI command is given a `--range` that starts after it (question 13, M-A), and the validator's sentence "Propose the change, or ask a maintainer to revert it" is
  changed in Task 14a-1 to say that rules cannot yet be proposed. What stays valid: writing the first rules (the
  history is judged from the commit that writes them), a solo or rule-less instance, and a rule the author may
  apply alone. Ratify is written so that adding document edits later
  changes the engine, not ratify (§3.8 step 3). Question 13 asks the operator whether that engine work
  belongs in P2.
- **No activity trail beyond the ledger and the log** (P3 reads them).
- **A stale proposal waits for its author**; no one else can resolve it, only withdraw is theirs and
  expiry is the clock's.
- **Nothing is migrated.** An instance with no `proposals.yaml` has no proposals; the file appears
  at its first Propose. Running P2 on a real instance is the operator's step.
