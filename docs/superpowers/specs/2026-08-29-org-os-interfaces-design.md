# org-os Interfaces — Consolidation Design Spec

**Date:** 2026-08-29
**Status:** Approved design, pre-implementation
**Owner:** interfaces contract + legacy-surface prune
**Companion to:** [`docs/MODULES.md`](../../MODULES.md) (catalog canon) · [admin app spec](2026-07-23-admin-app-design.md) · [KMS spec](2026-07-23-org-os-kms-design.md) · [multica spec](2026-07-24-multica-org-os-integration-design.md) · [modularization spec](2026-08-02-org-os-v5-modularization-design.md)

## 1. Purpose

org-os accumulated six interface experiments in six months because every new surface
invented its own access path to the instance repo — bespoke Fastify servers
(`agents-app`, `paperclip-agents-app`), static HTML snapshots (`dashboard`), template
webapps (`webapps/task-manager`). v0.5.0 shipped the surfaces that won (admin app,
org-os-kms, hermes, CLI) but still carries the losers in-tree, and nothing states the
rule that would prevent the next bespoke server.

This spec does two things:

1. **Declares the interface contract** — one contract, two planes, four surfaces —
   as the framework's access architecture.
2. **Prunes the superseded surfaces**, explicitly overturning the 2026-08-02
   modularization ruling that kept them as workspaces.

This spec owns the *access contract* (how anything reads or writes an instance).
`docs/MODULES.md` remains the catalog canon (what modules exist). On shape disputes
about data, `docs/DATA-MODEL.md` remains the source of truth.

## 3. The two-plane contract

An org-os instance repo is the source of truth. Everything that touches it does so
through one of two planes:

### Data plane (static, git-native)

`data/*.yaml` (registries, shapes per `docs/DATA-MODEL.md`) · `.well-known/`
(EIP-4824 exports, regenerated by `npm run generate:schemas`) · `graphify-out/`
(semantic graph) · `memory/`, `docs/`, `knowledge/`.

- **Read** by build-time and read-only consumers: org-os-kms, website-generator,
  federation peers, graphify.
- **Written** git-natively by *trusted local processes*: the CLI, skills, agents,
  the hermes runtime. Writes are guarded by schemas + `validate:*` and land as
  ordinary commits — the git log is the audit trail.

### Live plane (dynamic, served)

The admin app's Hono API + WebSocket events (`packages/admin/server/`, per the
[admin spec](2026-07-23-admin-app-design.md) §3) is the **only server** in the
framework. Registry CRUD, proposals, git operations, graph queries, and watch
events all flow through it. Every current and future live consumer — the admin
SPA, hosted admin v2, chat bots calling in, a future MCP server — is a *client*
of this API.

### The rule

> A new interface is a new **client** of one of the two planes.
> A new server, or a new write path, requires amending this spec.

This is the sentence that would have prevented `agents-app` and
`paperclip-agents-app` — both were parallel servers over the same repo the admin
API now serves.

## 4. The four canonical surfaces

| Surface | Audience | Plane | Home | Status (2026-08-29) |
|---------|----------|-------|------|---------------------|
| **CLI** | Operator in a terminal | Data (direct fs + git) | `scripts/initialize.mjs`, skills, npm scripts | ✅ Canonical since v1 |
| **KMS** | Public / researchers (read) | Data (build-time) | `packages/org-os-kms` | ✅ Shipped v0.5.0 |
| **Admin** | Stewards (read-write) | Live — it *hosts* the live plane | `packages/admin` | ✅ Shipped v0.5.0; defect fixes staging in 0.5.1 |
| **Conversational** | Operators/stewards via chat | Data plane today (hermes runtime); live-plane client as it matures | `org-os-hermes` module + `packages/multica-bridge` · `docs/CHAT-INTERFACE.md` | 🔨 in-dev |

Per-surface detail stays in each surface's own spec (linked in the header). This
spec owns the map and the contract; MODULES.md owns the catalog entries.

**Not surfaces:** `rad-org-os` and `org-os-website-generator` are distributions /
generators cataloged in MODULES.md; they consume the data plane and introduce no
server, so they need no entry here.

## 6. Release targeting

- **Now, on `main`:** this spec + the doc updates in §5 (docs-only, 0.5.1-safe).
- **0.6.0:** the package deletions, on a branch (e.g. `feat/interfaces-prune`)
  that merges after `npm run version:update 0.5.1` cuts the patch — matching the
  existing `feat/v06-integrations` worktree pattern. Rationale: removals don't
  belong in a patch reserved for the kms data-loss and admin defect fixes.

## 7. Verification

After the prune branch:

1. `npm run validate:structure` and `npm run validate:schemas` pass.
2. `npm run version:check` passes (all five version surfaces).
3. `npm run generate:schemas` runs clean.
4. `npm run render:templates` produces no diff referencing deleted paths.
5. Reference sweep: `grep -rn "agents-app\|paperclip\|packages/dashboard\|packages/webapps"`
   over tracked files returns only historical records (specs, plans, memory,
   CHANGELOG) — no live docs, scripts, or configs.
6. Admin app test suite still passes (`packages/admin` tests, including
   `real-data.test.ts` against this repo's registries).

## 8. Non-goals

- No physical restructure (`packages/interfaces/…`) — package homes stay as they are.
- No changes to the admin API surface, the KMS package, or hermes/multica behavior.
- No rewiring of the historical docs that mention deleted packages (plans, specs,
  research, memory are records and stay verbatim).
- No hub-side (`lf-zettelkasten-os`) or instance-side changes — this is
  framework-repo only.
