# DFOS × org-os Integration — Design Spec

**Date:** 2026-07-25
**Status:** Approved design, pending implementation plan
**DFOS:** https://protocol.dfos.com/ — open protocol for cryptographic identity and verifiable content (self-certifying `did:dfos` Ed25519 operation chains, content-addressed CIDs, public proofs / private content, relay network). Product layer: https://dfos.com/ (Metalabel's hosted "private internets": member-governed spaces with chat, posts, calendar, archive, treasury). Reference repo: https://github.com/metalabel/dfos (TS/Go/Python/Rust/Swift implementations, shared test vectors, CLI, official Claude Code skill `dfos@metalabel`).

## Goal

Give the org-os federation a cryptographic identity and verifiable-authorship layer via the DFOS protocol, staged so each phase ships standalone value: org + agent identities first, then content anchoring, then federation-wide verification, with the hosted spaces product as a research-gated tail.

The git substrate stays canonical. DFOS adds *proofs about* org-os state — who an instance is, who its agents are, who authored what — it never replaces storage, sync, or truth. This matches the protocol's own separation: the proof world is public and verifiable; content lives in private, member-governed spaces. org-os federation already works exactly this way (public `.well-known/` structure, private repos), so DFOS is the cryptographic backbone the model was missing.

## Decisions (locked)

| Question | Decision |
|---|---|
| Scope | Full stack, staged in one spec (protocol layers committed; hosted product exploratory) |
| Who gets DIDs | Org instances **and** their agents; humans keep existing identities for now |
| Content anchored | Federation manifests (`.well-known/`), knowledge-commons artifacts, governance decisions. **Not** memory/agent work logs |
| Relay strategy | Metalabel's hosted relay first; self-hosted federation relay in a later phase (relays have no trust hierarchy, so adding/migrating is cheap) |
| Spaces (hosted product) | Exploratory final phase, research-gated — no public API found as of 2026-07-25 |
| Integration mechanism | `packages/dfos-bridge/` wrapping the official `dfos` CLI + the official `dfos@metalabel` Claude Code skill for agent ops; `@metalabel/dfos-protocol` npm allowed inside the bridge where shelling out is awkward |
| Key custody | OS keychain via the CLI; keys never in any repo; CI signing deferred until custody is settled |

## Architecture

```
                    PUBLIC (proof world)                 PRIVATE (content world)
          ┌──────────────────────────────────┐   ┌─────────────────────────────────┐
          │  DFOS relay (Metalabel hosted;   │   │  org-os instance repos (git,    │
          │  self-hosted later)              │   │  canonical): data/*.yaml ·      │
          │  · org DIDs + agent DIDs         │   │  .well-known/ · knowledge ·     │
          │  · signed chains: manifest       │   │  memory/ · skills/              │
          │    anchors, artifact authorship, │   └───────────────┬─────────────────┘
          │    governance + countersigs      │                   │ reads/anchors
          └───────────────▲──────────────────┘                   │
                          │ publish/verify          ┌────────────▼────────────────┐
                          │                         │ packages/dfos-bridge/        │
                ┌─────────┴──────────┐              │  identity · credential ·     │
                │ dfos CLI           │◄─────────────│  anchor · verify             │
                │ (single binary,    │  wraps       │  (Node; npm lib internally   │
                │  OS keychain keys) │              │   where cleaner)             │
                └─────────▲──────────┘              └────────────▲────────────────┘
                          │ agent ops                            │ hooks into
                ┌─────────┴──────────┐              ┌────────────┴────────────────┐
                │ dfos@metalabel     │              │ generate:schemas ·           │
                │ Claude Code skill  │              │ verify:federation ·          │
                │ (official)         │              │ /initialize dashboard        │
                └────────────────────┘              └─────────────────────────────┘
```

Surfaces added to org-os:

- **`packages/dfos-bridge/`** — four modules: `identity` (create/resolve org + agent DIDs), `credential` (org DID issues scoped write credentials to its agent DIDs; revocation), `anchor` (compute artifact CID, append to the org chain, publish), `verify` (fetch and check peers' proofs).
- **`federation.yaml` v3.1** — `identity.dfos.did` for self; optional `dfos_did` per peer entry so trust levels can require a verified DID.
- **`.well-known/dfos.json`** — generated by `npm run generate:schemas`: DID, current chain head, relay hints. The machine-readable proof pointer peers fetch, sibling to `dao.json`.
- **`data/dfos.yaml`** — instance config: relay, key names, anchoring rules (which events anchor what).
- **Official Claude Code skill** — installed per workspace (`dfos skill install` or `/plugin install dfos@metalabel`); agents use DFOS the way DFOS designed for agents instead of us reimplementing workflows.

## Phases

### Phase 0 — Foundation (~half a day)

- Install the `dfos` CLI and the official skill in the org-os framework repo.
- Create one org DID locally (`dfos identity create`, no relay) for the framework repo itself — same dogfood-first pattern as the multica pilot.
- Document key custody: keychain location, backup/recovery procedure, what key loss vs key compromise each mean (rotation ops handle compromise; loss of an unpublished genesis is unrecoverable — back up before anything else).
- Smoke test: author a chain entry, verify it offline.

### Phase 1 — Federation identity (~1 day)

- Org DIDs for the hub and instances: lf-zettelkasten-os, refi-bcn-os, refi-dao-os, regen-coordination-os (refi-med-os when it exits bootstrap).
- One agent DID per instance; the org DID issues it a scoped write credential. Agent revocation = credential revocation, no org key rotation needed.
- Publish identities to the hosted relay (`--peer prod`).
- `federation.yaml` v3.1 fields + `.well-known/dfos.json` generation wired into `generate:schemas`.
- `npm run verify:federation` — walks `peers[]`, fetches each peer's `dfos.json`, verifies chain head signatures; reports verified / unverified / no-DID per peer.

### Phase 2 — Content anchoring: `packages/dfos-bridge/` (~2–3 days)

Anchoring rules (declared in `data/dfos.yaml`, executed by the bridge):

| Event | What gets anchored | Proof means |
|---|---|---|
| `generate:schemas` run | CID of `.well-known/` bundle | "This is org X's structure as of chain seq N" — peers verify who they federate with |
| Knowledge artifact published | CID of the artifact | Authorship + timestamp survive replication; counters silent scraping/AI-training claims |
| Governance decision recorded | CID of decision record (e.g. ReFi DAO steward election result) | Signed by the org; **witness countersignatures** requested from peer org DIDs (e.g. hub + refi-bcn witness a refi-dao result) |

- Anchoring is opt-in per event type and per instance; defaults conservative (manifests only).
- Countersignature requests/grants flow through the bridge's `credential` module; a decision record lists its witnesses in frontmatter.

### Phase 3 — Verification & sync (ongoing)

- `/initialize` dashboard federation section shows per-peer verification status (verified ✓ / stale / unverified).
- Evaluate a self-hosted relay for the federation (natural home: Regen Coordination infra) — the hosted relay remains a peer, nothing migrates destructively.
- Evaluate DFOS relay sync (gossip / read-through / sync peering) against koi-net for the real-time layer of FEDERATION.md; write up findings in `docs/integrations/dfos.md`.
- Optional CI auto-anchor GitHub Action — only after a custody decision for CI keys (a dedicated low-privilege anchoring credential, never the org genesis key).

### Phase 4 — Spaces (research-gated, hosted product)

- Pilot one org space manually — ReFi BCN is the natural candidate (real member community, local scope).
- Open the API conversation with Metalabel (same early-adopter work-in-kind posture as the KOI engagement).
- Only after both: design an org-os → space publishing bridge as its own spec. Nothing in Phases 0–3 depends on this phase.

## Safety

- **Publishing to a relay is an external action** → draft-and-present per CLAUDE.md until the operator explicitly whitelists specific anchor events in `data/dfos.yaml`. Local-only chain ops (create, author, verify) are repo-internal and autonomous.
- **Keys never in any repo.** OS keychain via the CLI; `~/.dfos/keys/` fallback is outside every repo; `.gitignore` guards added anyway in case of misconfiguration.
- **Agent credentials are scoped and revocable** — an agent DID can write only the chains its credential grants; compromise of an agent key never compromises the org identity.
- **The bridge never touches vault notes.** It reads `data/`, `.well-known/`, and published knowledge artifacts only. Vault-safety rules apply unchanged to every session.
- **Anchoring is additive** — a failed or skipped anchor never blocks `generate:schemas`, publishing, or `/close`.

## Error handling

- **Relay unreachable:** chains continue locally; publishes queue in the bridge and flush on next successful run. Verification degrades to "stale" (last-verified timestamp shown), never blocks a session.
- **CLI missing:** bridge degrades gracefully — commands report "dfos CLI not installed" with the install one-liner; nothing else in org-os breaks.
- **Verification failure for a peer:** surfaced prominently in the dashboard (possible key rotation or impersonation), but federation reads continue at the git trust level — DFOS raises the ceiling, it doesn't lower the floor.
- **Key loss:** documented recovery path (Phase 0); if genesis backup exists, rebuild; if not, new identity + peer re-verification — which is why backup precedes any relay publish.

## Testing

- **Bridge unit tests** against the real CLI in a temp `HOME` (throwaway keys, no relay): identity round-trip, credential grant/revoke, anchor produces a verifiable op.
- **One integration round-trip:** anchor an artifact as identity A, verify from identity B with no shared local state.
- **`verify:federation` fixture test:** synthetic peer set covering verified / stale / unverified / no-DID paths.
- **Protocol conformance is Metalabel's job** (their cross-language test vectors); we test the bridge, not the protocol.
- Uses the repo's existing `scripts/test` harness conventions.

## Alternatives considered

- **A. CLI bridge + official skill** — chosen: leans entirely on Metalabel's maintained tooling (CLI, skill, keychain custody, test vectors); minimal code to own; agents interact with DFOS the way its authors designed for agents.
- **B. Library-native (`@metalabel/dfos-protocol` npm only)** — cleaner in-process, but we'd own key management (the security-sensitive hard part the CLI already solves) and lose the official skill's workflows. Adopted only as an internal implementation detail inside the bridge where shelling out is awkward.
- **C. CI-first anchoring (GitHub Action leads)** — automatic and unmissable, but puts keys in CI secrets before custody thinking is done and keeps agents out of the signing loop. Deferred to a Phase 3 optional, with a dedicated low-privilege credential.
- **Spaces-first (product-led)** — rejected as the anchor: no public API found, and the protocol layers deliver value without the hosted product.

## Open questions (to resolve during implementation)

- Hosted relay terms, rate limits, and durability guarantees for third-party identities.
- Multi-machine key custody: the same org/agent identity operated from the Mac and the vacation/remote setup (iPad + Tailscale) — does the CLI support key sync, or does each machine get its own credentialed device key?
- Whether the hosted spaces product exposes any API/webhooks (Phase 4 gate) — ask Metalabel directly.
- refi-med-os inclusion timing (bootstrap status).
- Exact `dfos.json` shape — align with whatever `.well-known` convention the protocol community converges on, if any, before inventing one.
