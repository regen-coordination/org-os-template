## 1. Purpose

Two things, built together:

1. **The platform** becomes the one place an organization is run from: every record, every running
   part, and every outside system the org uses (its Safe, its Gardens pools, its docs, its databases)
   framed in one interface. A member never edits the repo directly through it. They stage a change,
   and the change follows the org's own governance before it lands.
2. **The framework, org-os 0.6**, is rebuilt around a short set of definitions that the platform,
   the modules and the agents all use, so the loop the platform runs is a property of org-os itself
   rather than of one app.

This document fixes those definitions and how the pieces depend on each other. Each piece is then
specified and built in its own spec (§8). Nothing here is code.

## 3. The loop

Every change to the organization travels the same path, whoever makes it, whatever it touches:

```
 record ──edit──▶ change ──propose──▶ proposal ──rule──▶ decision ──▶ record updated
   ▲               (staged)                       (the org's own)        │
   └──────────────────────── activity: the git log, read back ◀─────────┘
```

- A **change** is private and cheap: staged edits across any number of records, with one combined
  diff.
- A **rule** says, for each class of change, who may propose it and how it is decided.
- Under a rule that lets the author decide alone, *Apply* is the decision, and it commits at once.
  That is the rule for a solo-maintainer instance like example-solo-os, and nothing about it feels like
  bureaucracy.
- Under any other rule, the change becomes a **proposal** that waits for what the rule requires: an
  approval, an objection window, a vote, or an outcome on an outside system such as a Safe threshold
  or a Gardens pool.
- The **decision** is recorded, the records update in one commit, and the commit's trailers make
  the whole trail readable from `git log`.

Same screens, same loop, different rules. example-solo-os (solo maintainer) and example-coop-os (consent
among three maintainers, with an objection window) differ by one block of YAML.

## 4. The definitions

Each definition says what it is, where it lives, its shape, who writes it, and what must always hold.
Shapes are sketches: the first spec that implements a definition fixes its JSON Schema, and that
schema becomes the canon.

### 4.1 Record

**What.** One entry in a `data/*.yaml` registry (a *collection*), or a whole registry file (a
*document*, such as `governance.yaml`). This is the existing model, made canonical.

**Where.** `data/*.yaml`, with schemas in `packages/admin/schemas/`. The registry list in
`server/registries.ts` is the one list of registries; `DATA-MODEL.md` documents it and is checked
against it.

**Identity.** A record's id is `<kind>:<id>`, the same ids the board's resources use today. Links
between records are the board's edge kinds, made schema fields rather than adapter inference.

**Must hold.**
- Schemas accept what real instances contain. Today `governance.schema.json` rejects
  `solo-maintainer` (the framework, example-solo-os) and `consensus` (example-coop-os), which 0.6 fixes.
- Aliases resolve (`opportunities` / `funding_opportunities`), as they do today.

### 4.2 Member and actor

**What.** A *member* is a person or agent in the org. An *actor* is the member a request is made
by.

**Where.** `data/members.yaml`. Each entry gains:

```yaml
- id: ana                       # stable, referenced by rules, proposals and decisions
  name: Ana Example
  kind: person                  # person | agent | organization | role (default: person)
  handles:                      # how an actor is recognised
    git: ana@example.org
    github: ana-example
    address: eip155:42220:0x…   # optional: a signer on a Safe, a voter in a pool
```

**Ids are opaque.** They are unique within an instance and never parsed. Real instances already
use five styles (`github:…`, `did:…`, `exampledao:role:…`, bare slugs), and the same person carries a
different id in each repo. Identity across instances goes through `handles`, never through the id.

**Governance roles are not on the member.** Which members are maintainers is stated once, in
`governance.yaml` `roles` (§4.5). The vault hub already uses a member-level `roles` field for its
affiliations (`[{org, role}]`), and a second meaning on the same key would collide.

**Resolving the actor.**
- **Local** (the platform on your machine): the actor is the member whose `handles.git` matches the
  repo's `git config user.email`.
- **Hosted** (platform spec 5): the actor is whoever signed in. The members file decides what they
  may do; sign-in only proves who they are.
- **Agents** (crew seats) are members with `kind: agent`. They may stage and propose. No rule may
  name an agent as a decider. This writes "the operator holds final authority"
  (`roles/README.md`) into the model.
- **No matching member:** the platform is read-only, and says why.

### 4.3 Change

**What.** A staged set of structured operations on records. Changes are not text diffs.

```json
{ "id": "chg_…", "actor": "ana", "created": "…",
  "ops": [
    { "op": "update", "record": "project:river-commons",
      "base": "<sha of the entry as staged>",
      "set": { "stage": "develop" } },
    { "op": "create", "record": "partner:example-network", "value": { … } }
  ] }
```

**Where.** In the admin state directory, outside the repo
(`~/.org-os/admin/<instance>/changes/<actor>.json`, today's `stateDir`), so staging never dirties the working tree and
never trips the server's dirty-file guard. One open change per actor; it is the *Changes* tray.

**Must hold.**
- Every op carries the `base` hash of the entry it was staged against. Applying checks each base
  first. A mismatch marks only that op **stale**, and the tray shows the record's current value next
  to the staged one.
- Because ops are structured, bringing a change up to date means replaying its ops onto the current
  records. No git rebase is ever needed, which matters, because the safety rules forbid the forced
  operations the July M3 design relied on.
- Validation runs at stage time (an error shows on the field) and again at apply time.

**Change classes.** Every op is classified, and rules key on classes:

| Class | Covers |
|---|---|
| `records` | routine registry entries: projects, funding, partners, ideas, meetings, events… |
| `members` | `members.yaml`, roles included |
| `governance` | `governance.yaml`: rules, roles, the decision record itself |
| `identity` | `IDENTITY.md`, `federation.yaml`, `.well-known` identity fields |
| `systems` | `data/systems.yaml`: adding a Safe, changing a pool |
| `treasury` | actions on a System of kind `safe` (§4.8) |
| `operations` | running a nonce-gated operation that changes something (today's executor) |

The classification is a fixed table in the framework. An instance can split a class (for example
`records:funding`) but cannot remove one.

### 4.4 Proposal

**What.** A change sent for decision under a rule.

**Where.** The *trunk* is the branch the platform serves for the instance.
- Metadata lives in `data/proposals.yaml`, committed on the trunk so every member sees it.
- The content lives on a `proposal/<id>` branch, built from the trunk by replaying the ops in a
  fresh worktree under the admin state directory. Rule evaluation and the diff view read the branch;
  nothing else does.

```yaml
proposals:
  - id: p-2026-10-17-001
    title: Move River Commons to develop; add Example Network as partner
    rationale: …
    author: ana
    classes: [records]
    rule: records            # the rule id it was opened under (§4.5)
    branch: proposal/p-2026-10-17-001
    state: open              # open | ratified | rejected | withdrawn | expired
    opened: 2026-10-17T10:02:00-03:00
    events:                  # append-only; the input to rule evaluation
      - { at: …, by: bruno, kind: approve }
      - { at: …, by: carla, kind: object, text: … }
```

**Lifecycle.**
- A draft is the actor's open change. It lives in the state directory, not here.
- *Propose* creates the branch and writes the `open` entry. Every event after that (approve, object,
  vote, withdraw) is a small commit to `proposals.yaml`, so the git log is the audit trail.
- **Ratified** means the branch merges into the trunk without fast-forwarding, the decision is
  recorded (§4.6) and `generate:schemas` runs.
- **Rejected**, **withdrawn** and **expired** proposals keep their branch. It is never force-deleted.
  It is listed as closed, and the proposal entry records why.

**Must hold.**
- Opening, deciding and merging are server operations on the live plane. They use plain
  `git branch`, `git worktree add/remove` (only when clean) and `git merge`. There is no `--force`,
  `-D`, stash, clean or reset.
- A proposal goes stale when the trunk moves under its ops. Bringing it up to date replays the ops
  onto a new branch commit and records an event.

### 4.5 Rule

**What.** A machine-checkable statement, per change class, of who may propose and how a proposal is
decided.

**Where.** `governance.yaml` gains `roles` and `rules`. The existing prose fields (`model`,
`description`) stay as the human summary.

```yaml
governance:
  model: consensus
  description: "Consent-based decision-making with objection window"
  roles:
    maintainer: { members: [ana, bruno, carla] }
    member:     { all: true }                       # every person in members.yaml
  rules:
    - id: records
      applies_to: [records]
      propose: member
      decide: { by: maintainer, method: approve, count: 1 }
    - id: governance
      applies_to: [governance, members, identity, systems]
      propose: maintainer
      decide: { by: maintainer, method: consent, window: P7D }
    - id: treasury
      applies_to: [treasury]
      propose: maintainer
      decide: { by: system, system: treasury-safe }  # the Safe's own threshold decides
```

**Methods.**

| Method | Decided when |
|---|---|
| `direct` | The author is in `by`. *Apply* is the decision, and no proposal is opened. |
| `approve` | `count` members in `by` approve and none of them objects. |
| `consent` | `window` elapses with no objection from `by`. An objection holds it open until withdrawn or answered by a revision. |
| `vote` | `quorum` members in `by` vote, and `threshold` of the votes cast are yes, within `window`. |
| `system` | The named System reports an outcome: a Safe transaction executed, a Snapshot proposal passed, a Gardens proposal funded. The platform reads the outcome (§4.8). It never manufactures one. |

**The solo default.** An instance whose `model` is `solo-maintainer` and that has no `rules` behaves
as if it had exactly one rule: `{ applies_to: [all], propose: maintainer, decide: { by: maintainer,
method: direct } }`. example-solo-os and the framework work unchanged on day one.

**Must hold.**
- **Rule evaluation is one pure function:** `evaluate(rule, proposal, members, now) → { state,
  missing }`, where `missing` is the sentence the platform shows ("needs 1 more approval from a
  maintainer", "objection window closes in 2 days"). It has no I/O, so every method is tested
  exhaustively.
- **Rules that govern rules.** A change to `rules` or `roles` is class `governance`, decided under
  the rule in force when it was proposed, never the rule it introduces.
- A rule that names an agent in `by`, or a role with no members, fails validation.

### 4.6 Decision

**What.** The record that a proposal was decided, and how.

**Where.** `governance.yaml` `decisions[]` is the one machine record:

```yaml
decisions:
  - id: gov-20261017-001
    proposal: p-2026-10-17-001
    rule: records
    method: approve
    outcome: ratified          # ratified | rejected | expired
    by: [bruno]                # who carried it
    date: 2026-10-18
    title: …
    summary: …
```

**`DECISIONS.md`** stays the prose record for decisions that carry reasoning. A proposal can be
marked *record as decision* (always for classes `governance` and `identity`). Ratifying it then
appends a `DECISIONS.md` entry in the instance's own convention (`LD-` ids in example-solo-os) that
points back at the proposal.

**What is not a decision.** A `direct` apply of class `records` creates no decision row. The commit
is the record, and its trailers say so. Otherwise a solo instance would write a governance entry for
every typo.

**Commit trailers.** Every commit the platform makes carries them, and the activity trail (platform
spec 3) reads them back from `git log`:

```
Org-Actor: ana
Org-Change: chg_…
Org-Rule: records/direct
Org-Proposal: p-2026-10-17-001        # when there was one
Org-Decision: gov-20261017-001        # when one was recorded
```

### 4.7 The tight part: what stops a change going around the loop

The data plane stays writable by trusted local processes (the interfaces spec, §3). The CLI, skills
and agents still commit `data/*.yaml` directly. Tightness comes from checking, not from locking the
files:

- **`npm run validate:governance`** (new) reads the commits on a branch. A commit that touches a
  governed class (anything whose rule is not `direct` for its author) without an `Org-Proposal`
  trailer naming a ratified proposal is an **error in CI** and a **warning locally**.
- The instance doctor reports instances whose rules and history disagree.
- Agents commit only on `crew/*` branches, as they already do. Merging their branch is itself a
  proposal once the instance's rules say so.

### 4.8 System

**What.** An outside system the org uses, framed in the platform: a Safe, a Gardens pool, a
Snapshot space, a Hats tree, a docs space, a database, a KMS connector's source.

**Where.** `data/systems.yaml` (new):

```yaml
systems:
  - id: treasury-safe
    kind: safe
    name: Treasury
    chain: eip155:42220
    address: "0x967c04deCA1e3a0DA6ac08E2D1bb3c7A70B0cb60"   # a generated address (fakeAddress), standing in for an instance's Safe
    driver: safe                 # which driver reads it
    section: organization/treasury
  - id: shared-drive
    kind: docs
    name: Shared drive
    url: https://…
    driver: link                 # no reads: a framed link-out
    embeddable: false
```

**Drivers.** A driver is a server-side module on the live plane, in the same shape as today's
resource adapters:

```
read(ctx)        → { facts, attention, items[] }    // cached; a timeout or failure becomes attention, never a crash
actions          → [{ id, class, label, prepare(change) → artifact }]
outcome(ref)     → { state: pending|passed|failed|executed, detail }   // for rules with method: system
open             → { url, embeddable }
```

**Must hold.**
- **The platform never signs, sends or holds keys.** `prepare` yields an artifact: for a Safe, the
  transaction payload and a link to open it in the Safe app. Submitting that payload to a service
  (for example the Safe Transaction Service) is an external write. It is a nonce-gated operation
  that a signer runs and confirms, which keeps draft-and-present.
- Network reads are cached per System with a stated age ("read 4 min ago"). A failed read shows
  as attention on that System, and the rest of the platform is unaffected.
- KMS connectors keep their own contract (the July connector-layer spec). A `kms-connector`
  System entry points at one, so the platform frames it without a second driver.

**Migration.** `governance.yaml` `infrastructure` (`safe`, `hats_tree`, `gardens`, `snapshot`)
moves into `systems.yaml` entries. `finances.yaml` `treasury_snapshot` stays as the offline
fallback, and the platform labels it as a snapshot with its date.

### 4.9 Module

**What.** The existing versioned unit of capability (`modules/*/module.yaml`), which can now
declare what it contributes to the platform.

```yaml
platform:
  kinds:      [{ kind: pool, section: organization/pools, board: organization }]
  adapters:   [packages/gardens-integration/platform/adapter.ts]
  drivers:    [{ kind: gardens-pool, module: packages/gardens-integration/platform/driver.ts }]
  operations: [packages/gardens-integration/platform/operations.ts]
  classes:    [{ class: treasury, covers: "pool funding proposals" }]
```

**Must hold.**
- A module adds kinds, adapters, drivers, operations and class splits. The platform renders them
  with its generic pages: a list, a record page, a map node, an inspector. **Modules do not ship UI
  in 0.6.** Custom pages wait until two modules need the same thing a generic page can't do.
- The v5 module schema (`additionalProperties: false`) gains the `platform` block. The module
  engine frozen in the August portfolio memo (row 2) is un-frozen for this. Its trigger, two
  manifests, already fired at v0.5.

## 5. How the pieces depend on each other

```
            ┌──────────────────────────── clients ───────────────────────────┐
            │  platform (web)   cockpit/CLI   conversational   crew agents    │
            └──────────────┬─────────────────────────────────────────────────┘
                           │  HTTP + WebSocket (the only server)
 live plane  ┌─────────────▼──────────────────────────────────────────────────┐
             │ resources ← adapters ← module adapters                          │
             │ change engine (stage · apply · replay) ── rule evaluator (pure) │
             │ proposals (branch · worktree · merge) ── decisions + trailers   │
             │ system drivers (read · prepare · outcome)   operations/executor │
             └─────────────┬──────────────────────────────────────────────────┘
                           │  reads/writes, git
 data plane  ┌─────────────▼──────────────────────────────────────────────────┐
             │ data/*.yaml: records · members · governance (roles, rules,     │
             │ decisions) · proposals · systems     DECISIONS.md     git log  │
             └────────────────────────────────────────────────────────────────┘
```

- Clients depend only on the API. The platform is the first client and not a special one.
- The change engine depends on records, members and rules. The rule evaluator depends on nothing.
- Drivers depend on systems and on the network. Everything above them tolerates a driver that
  fails.

## 6. What 0.6 does not do

- It does not custody funds, sign, or execute on chain. It reads, prepares, and frames.
- It does not replace Snapshot, Gardens or a Safe's own threshold. Rules with `method: system` read
  their outcomes.
- Modules ship no UI of their own (§4.9).
- There is no sign-in until platform spec 5. Until then the actor is the local git identity, and
  multi-member governance is exercised by members on their own machines, with proposals reaching
  each other through the shared remote.
- It does not move the data plane off git.

## 7. Amendment to the interfaces spec (§3)

The live plane gains three things. The interfaces spec's rule requires an amendment for a new write
path, and this is it:

1. **The change engine and proposals** are the platform's write path for records. The existing
   `PUT/POST/DELETE /api/registries/…` routes become "stage and apply under the author's rule". They
   keep working for an author whose rule is `direct`, and they return the proposal they opened
   otherwise.
2. **System drivers** read outside networks from the server: Safe Transaction Service, subgraphs,
   docs APIs. Each driver declares its hosts. The server's guard does not change.
3. **External writes** (submitting a prepared artifact to an outside service) are a new class of
   operation, nonce-gated like today's `changes`/`network` operations, and always confirmed by a
   person.

## 11. Defaults this document chose (open to revision at review)

- One open change per actor, rather than several named drafts. Simpler tray; revisit if people
  juggle unrelated edits.
- Staged changes live outside the repo, in the admin state directory, so they are not shared until
  proposed.
- Rejected proposal branches are kept forever. Pruning them would need `-D`, which the safety rules
  forbid.
- `consent` defaults to a 7-day window when an instance's prose names a window without a length.
  The doctor asks the operator to confirm it.
- The first live driver is the Safe (read-only), because example-coop-os has a real one on Celo and the
  Safe Transaction Service is public.
