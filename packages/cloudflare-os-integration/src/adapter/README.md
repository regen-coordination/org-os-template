# Adapter wiring runbook — `gatekeeper-org-os`

How the pure core in `../` becomes a live Cloudflare OS gatekeeper. Mirrored into
`docs/integrations/cloudflare-os.md` §"Adapter wiring runbook".

**Status:** verified against a **local** Cloudflare OS stack (upstream pinned `1cb5e3d`,
2026-08-07) on 2026-08-08. Deployed-workspace verification is pending a Cloudflare account.

## What lives where

| | Canonical home | Notes |
|---|---|---|
| Page core, substrates, capabilities | `packages/cloudflare-os-integration/src/` (this repo) | 86 tests; the meaning |
| Adapter Worker source | `src/adapter/gatekeeper-org-os/` (this repo) | The files below |
| Running Worker | `<cf-workspace>/packages/gatekeeper-org-os/` | A **copy**; see Install |
| Vendored core inside the Worker | `<cf-workspace>/packages/gatekeeper-org-os/vendor/org-os-core/` | Generated by `sync:core` — never edited |

The Cloudflare OS workspace is a separate pnpm workspace and cannot resolve a sibling repo, so
the core is **vendored by copy** rather than depended on. `scripts/sync-core.mjs` performs the
copy and `git diff vendor/` shows drift. The org-os repo stays canonical in both directions.

## Install

```sh
# 1. Copy the adapter into the Cloudflare OS workspace
cp -R src/adapter/gatekeeper-org-os <cf-workspace>/packages/

# 2. Pull in the core and generate the agent-facing type text
cd <cf-workspace>/packages/gatekeeper-org-os
ORG_OS_REPO=/path/to/org-os node scripts/sync-core.mjs
node scripts/sync-types.mjs

# 3. Generate Worker types, then point mainModule at src (not the build output)
pnpm exec wrangler types
sed -i '' 's|"./.wrangler/validate/src/org-os"|"./src/org-os"|' worker-configuration.d.ts

# 4. Verify
pnpm run types:check          # must be silent
cd <cf-workspace> && pnpm install && pnpm run-local
```

**Registration is automatic.** `run-dev-server.js` scans `packages/` for `gatekeeper-*`
directories containing a `wrangler.jsonc` and generates the `GATEKEEPER_ORG_OS` service binding
into `wrangler.dev.jsonc`. There is no config file to edit. On the starter's deploy path the
equivalent slot is `workers.customGatekeeper.name` in `deployment.jsonc`, bound by
`scripts/deploy.mjs`.

Step 3's `sed` is not cosmetic: `wrangler types` writes `mainModule` pointing at
`.wrangler/validate/`, which drags the generated capnweb shim into the TypeScript program and
produces errors in code you did not write. Upstream's own gatekeepers point at `src/`.

## Configuration

**`ORG_OS_INSTANCES`** — a `vars` entry in `wrangler.jsonc`, a JSON array. Repository coordinates
are public information; this is deliberately not a secret.

```json
[
  {"id":"org-os","owner":"regen-coordination","repo":"org-os-template","ref":"autopoiesis-phase2-pilot"},
  {"id":"refi-bcn-os","owner":"refibcn","repo":"refi-bcn-os"}
]
```

`ref` defaults to `main`. The hub is pinned to the work branch because the integration is not on
`main` yet — **change this to `main` when the branch merges**, or the gatekeeper will keep reading
a stale branch.

**`ORG_OS_GITHUB_TOKEN`** — a Wrangler secret, never config:

```sh
pnpm exec wrangler secret put ORG_OS_GITHUB_TOKEN --name gatekeeper-org-os
```

Fine-grained PAT, **`contents: read` only**. `regen-coordination/org-os-template` is public and
readable without one (at 60 req/hr instead of 5,000); `refibcn/refi-bcn-os` is **private** and
requires it. Because fine-grained PATs are scoped to a single resource owner and these repos sit
under two different organizations, one token cannot be minted for both — scope it to `refibcn`,
which is the repo that actually needs authentication. Do not grant `pull-requests:write`; nothing
before M3 can open a PR.

## Cache backing

In-memory `Map`, held on the `OrgOsGatekeeperImpl` Durable Object instance. A DO is
single-threaded and long-lived, so this gives real ETag/TTL reuse across requests without the
async round-trip DO storage would add to every read. Eviction costs one revalidation, not
correctness. Revisit if a deployment needs cache sharing across DO instances.

## Security posture — read this before widening access

The gatekeeper is auto-provisioned and reads through **one deployment-level token**, not per-user
OAuth. Consequences:

1. Every authenticated workspace user has identical access to identical repositories.
2. `addObserver()` is therefore unconditional — there is no per-user authority to compare, and an
   observer can never see data a peer could not read through this same gatekeeper.
3. **A private instance's contents are readable by every workspace user.** The security boundary
   is workspace membership, enforced upstream at sign-in.

That is a deliberate property of the deployment-token design, not an oversight, and it is safe
only while workspace membership ≈ org membership. **If the federation ever needs per-user access
differentiation, this must become per-user OAuth and `addObserver()` must gain a real check.**
The comment in `org-os.ts` says the same thing at the call site.

Every read calls `authorizeObservation()` *before* fetching, so an observation the user would
deny never reaches GitHub.
