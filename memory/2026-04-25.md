### Key Decisions

- **Phased a → b → c.** Phase (a) = CLI commands + multica-as-runtime + write-only HEARTBEAT bridge. Phase (b) = bidirectional sync. Phase (c) = org-os published as a multica plugin.
- **Self-hosted multica via bundled docker-compose** (Postgres+pgvector + multica server). Sovereignty-aligned; no SaaS dependency. Multica Cloud deferred to phase b.
- **multica = primary AgentRuntime; openclaw demoted to alternative-runtime.** openclaw stays in `data/instances.yaml` and `federation.yaml` — not removed, just role-swapped.
- **Bridge runs both manually (`npm run bridge:multica`) and automatically on `/close`.** Failure is non-fatal — `/close` warns and continues.
- **Idempotency via sha1(category + "|" + normalize(text)).** Re-runs upsert; tasks missing from HEARTBEAT.md get closed in multica with reason `removed-from-heartbeat`.
- **multica-integration is the *pilot* for the queued `package-integration` plan's Phase 3 question.** Establishes "self-installing package with bundled `install.sh` + `docker-compose.yml`" as the proposed canonical pattern. Parent plan retains authority to ratify.
- **Pull `lifecycle_status` field on `packages-matrix.yaml` forward** from the parent package-integration plan since this spec needs it. Backfill all entries to `active`; full reclassification stays with the parent plan.
- **No vendoring of multica source.** 52 releases at time of spec — pin would rot. Thin glue, like `hermes-integration` and `opencode-integration`.
