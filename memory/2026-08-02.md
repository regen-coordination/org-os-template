## Session — 10:51

**Focus:** Federation map ("the torch") — an interactive visual of an instance's *external* world (federated instances, frontier peers-of-peers, sources/provenance, ecosystems), designed as the deliberate counterpart to the internal note graph. Full cycle: brainstorm → spec → 14-task TDD plan → subagent-driven execution → holistic review → security fix.

### Key Decisions

- **Surfaces = A + C.** A reusable package instances embed on their public sites, *plus* an operator-side vault artifact openable next to Obsidian's graph. (Rejected: site-only.)
- **Two linked views, not one blended space.** The map is strictly external; crossings between the internal note graph and the map are explicit deep-link portals. Keeps the data model clean and preserves "inside vs outside" as a meaningful distinction.
- **Depth = frontier + curated ecosystems.** Fetch each ring-1 peer's own `federation.yaml` one hop out to render peers-of-peers as dim ring-2 nodes, plus hand-curated ecosystem nodes from `data/ecosystems.yaml`. This is what makes the dark-forest metaphor literal — you see fires you haven't walked to.
- **Visual language = hybrid** (operator chose "all + hybrid"): orbital structure (deterministic rings by hop-distance) × constellation physics (d3-force, draggable, kin to Obsidian's graph) × torchlight atmosphere (luminosity falls off with distance; frontier = embers).
- **Packaging = framework-agnostic web component**, not an Astro component library. `<federation-map>` with d3-force as its only dep; a thin Astro wrapper in `site/` gives Astro ergonomics with zero lock-in. Revisit a real Astro library later if warranted.
- **Strict view/data split.** `org-os-kms` owns aggregation (`render map` → `map.json`); the component never reads YAML. Swap the host, keep the view; swap the view, keep the data — same seam philosophy as kms itself.
- **Frontier fetch is a separate op from rendering.** `render map` reads only the cache, so network failures can never break a build. Stale cache beats broken build.
- **Executed on the `v0.5` trunk, not an isolated worktree.** Packages resolve siblings by relative path and live-enrichment reads real sibling clones; a worktree would have cost a full dep reinstall and hidden the real data. Trade-off accepted deliberately.
- **Deviation from spec §5 (recorded):** portal *index* file (`renders/federation-portals.md`) instead of stamping links into individual KB notes — KB objects are YAML registry rows today, not markdown notes, so there are no boundary notes to stamp yet.

## Session — 11:00

**Focus:** Scoping the integration of [graphify](https://github.com/Graphify-Labs/graphify) into `packages/org-os-kms`. Exploration + architectural read only — **no code written**; the session closed before the scope question was answered.

### Findings

**The two systems are complements, not overlaps** — they sit at opposite ends of the same pipeline:

| | `org-os-kms` (+ `toolkit-framework`) | `graphify` |
|---|---|---|
| Language | Node.js ESM, near-zero-dep | Python 3.10+, PyPI `graphifyy` |
| Method | Human-in-the-loop curation | Automated deterministic extraction |
| Unit | Typed schema objects (resource, source-system, concept-lineage, signal, contribution-record, encyclopedia-entry) | Graph nodes + edges over ~40 languages |
| Provenance | K1 maturity states, lineage stamps, `csis-review` on `/close`, review queue | `EXTRACTED` vs `INFERRED` edge confidence |
| Output | `data/*.yaml` org-os registries + federation | `graph.json` / `graph.html` / `GRAPH_REPORT.md` |
| Query | none (registries are flat lists) | `query` / `path` / `explain`, MCP server, REST server |

The headline gap each fills for the other: **kms has no graph-query capability**; **graphify has no curation, provenance, or federation model**.

### Integration surfaces identified

- **Ingest seam** — `toolkit-framework/src/ingest.mjs`: `classifySource` → `chunkContent` → work orders → agent extraction → `acceptWorkOrder` (validates, stamps lineage, atomic accept). graphify's `graph.json` could enter here as pre-extracted candidates. Note `INGESTIBLE` is currently `.md/.markdown/.txt/.csv` and `classifySource` knows nothing about code or JSON graphs.
- **Adapter seam** — `toolkit-framework/src/adapters/` (`repo-data`, `geo`, `kb-folder`); a `graphify` adapter would slot alongside.
- **Op/lifecycle seam** — `kms/src/ops.mjs` `OPS` registry maps op-names → `{kind:'exec'|'skill', write:bool}`; `bind.mjs` `LIFECYCLE_BINDINGS` sequences them for `initialize`/`close`. A `graph.build` / `graph.query` op drops in declaratively.
- **Profile seam** — `kms/profile/profile.yaml` bundles what every instantiated instance gets out of the box.
- **CLI seam** — `kms/src/cli.mjs` `VERBS` set (`lifecycle bridge render federate promote init`).

### Key architectural question (unresolved)

**Node ↔ Python is the forcing constraint.** Three ways across, undecided: subprocess to the `graphify` CLI · talk to its MCP server · talk to its REST server. This choice ripples through packaging (does an org-os instance now require a Python toolchain?), CI, and the "near-zero-dep" posture kms has held so far.

### Open scope question put to the operator (unanswered)

Which is the *center of gravity*:
- **A) Ingest source** — graphify extracts a repo/folder → candidates feed the framework ingest pipeline through the normal review/lineage/federation flow.
- **B) Query engine** — build a graph over the instance's *own* registries/KB, then expose `query`/`path`/`explain` + MCP over the commons (fills kms's biggest gap).
- **C) New adapter** — a `graphify` storage adapter beside `repo-data`/`geo`/`kb-folder`.
- **D) Full bundle** — ship graphify in the kms *profile* so every instance gets graph intelligence by default.

- **graphify has already been run against this repo.** Untracked `graphify-out/` exists (`.graphify_root`, `.graphify_python`, and a 2.8MB `graph.html`, generated 2026-07-22→26). Neither it nor `site/test-results/` is in `.gitignore` — a 2.8MB generated artifact is one `git add -A` away from the history. Worth ignoring before any integration work starts.
